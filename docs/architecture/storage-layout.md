# Storage layout: which store holds each table, and why

Each Loom table belongs in Postgres or ClickHouse by how it is read and written; this
page places every table, with the wave that moves it. Postgres holds state read by key,
changed in place or locked, and ClickHouse what is appended and scanned ([storage
authority](storage-authority.md)). The page sets out:

- the rule that places a table by its access pattern, and the schema rules of each
  store;
- the shared Postgres structures that replace queues, claims and leases built on
  ClickHouse, and how statements that cross the two stores are rewritten;
- a row for every ClickHouse and Postgres table, with its store, key, kind and erasure
  coverage, and for a ClickHouse table up to two modules whose statement, table-name
  literal or table constant names it;
- the [waves](#waves), how a table moves, and what a restore keeps.

A table's Today column is where it is now, until its wave ships. A table added later
follows the same rule, and the change that adds it adds its row here.

## The placement rule

A table goes to the store whose guarantees its readers depend on.

| A table goes to **Postgres** when it is                                                                           | A table goes to **ClickHouse** when it is                                                            |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| read by key, and a reader needs the value as of the last commit (a revocation, a grant, a policy, a lock, a head) | appended and scanned: vectors, terms, chunks, statistics, the graph projections, the code index      |
| changed in place: a status, a lease, a cursor, a counter two replicas must agree on exactly                       | history: version rows, append-only and changed only by erasure and, for `memory_versions`, redaction |
| claimed or locked: a queue, an outbox, a lease, a claim, a compare-and-set                                        | a log or a rollup: events, traces, audit, usage, cost, exposures, SLIs                               |
| small per tenant: registrations, configuration, user-written state outside the search corpus                      | a cache with a TTL: provider answers, search memos                                                   |

State that search joins with the memories inside ClickHouse (operator-authored
`categories` and the `memory_categories` links, `server/memory/domain/search_sql.py`)
stays in ClickHouse even when it is small and per tenant. Its by-key reads need no
Postgres commit: the import's insert-if-absent read of the links (`link_states` in
`server/memory/store/categories.py`) runs with sequential consistency, and a duplicate
link collapses on the `ReplacingMergeTree` key; the registry read of
`memory.assign_category` and `memory.import` (`registered_ids`) runs without it today,
so on a lagging replica a category registered a moment before answers
`CATEGORY_NOT_FOUND` or skips the import's link, and wave 3 reads it with sequential
consistency too.

Each test comes from a cost ClickHouse pays today for state it does not fit:

- **`FINAL` on point reads.** A `ReplacingMergeTree` read by key under `FINAL` merges
  the key's parts at read time, so its latency depends on how far merges are behind.
- **Merge-dependent correctness.** Without `FINAL`, a read sees every version until the
  merge; with a cache in front, the cache must fail closed when the read fails
  (`revoked_tokens`, `namespace_grants`).
- **No row locks.** A queue on `ReplacingMergeTree` claims an item by inserting a
  version and reading back who won (`memory_extraction_queue`), or records an item's
  state by a mutation (`memory_projection_failures`), and keys of the KeeperMap table
  `loom._migration_lock` stand in for compare-and-set and for leases
  (`server/core/leases.py`). A KeeperMap key is not in a transaction with the rows it
  guards, and it gives its holder no fencing token.
- **No transactions.** A change that must touch two tables together (a task and its
  lease, a job and its cancel) is written as two inserts with reconciliation code
  between them.

A table that needs both a current value and a scan splits, as memory does: the head in
Postgres, and in ClickHouse a projection of it, published from the commit, that the
scans, joins and history views read.

### Each fact has one owner

Every table is one of five kinds. Each store is backed up whole (a ClickHouse backup of
the `loom` and `loom_telemetry` databases, a Postgres backup of the cluster), so every
table is in its store's backup. A ClickHouse backup copies each table at a slightly
different moment, so a ledger that says how far a table is built may come back ahead of
or behind it. The ledger rule, which every other section points to, sets each after a
ClickHouse restore:

- A ledger whose output is idempotent to re-run is reset to no later than its output (a
  ledger keyed by a commit, `code_index_state`, forces a full re-diff).
- A ledger that keeps output from being written twice (`usage_acted_credits`, whose
  output `memory_usage_events` does not collapse duplicates) is set no earlier than its
  output, by rebuilding it from that output, which wave 4 makes possible by putting the
  pair digest on each `acted` event.
- A Derived table fed by a view from its source (`entity_degree`, `memory_usage_totals`,
  the term and document-length folds) is reconciled or rebuilt from its source, except a
  table that is SoR past its source's retention (`subject_last_seen`,
  `agent_cost_rollup_daily`, `loom_telemetry.sli_minute`), which is only refolded over
  the source's retained window, never truncated or rebuilt whole.
  `conversation_embeddings`, written directly and SoR past its messages' retention, is
  re-embedded only for retained messages and never truncated.

The kind says what is lost, and what a rebuild needs, when a backup is not there:

| Kind        | Meaning                                                                                                                                    | Without a backup                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| **SoR**     | system of record: the only copy of the fact                                                                                                | lost                                                          |
| **Log**     | an append-only system of record, often with a retention TTL (in the schema, or set by `retention_reconcile`): events, traces, audit, usage | history is lost, not correctness                              |
| **Derived** | rebuilt from a named source; the row says from what, and whether the rebuild calls a model                                                 | rebuilt from its source, at a model's cost where it calls one |
| **Cache**   | expendable: provider answers, memos, published assets                                                                                      | nothing; it refills                                           |
| **Coord**   | coordination state: leases, claims, acknowledgements, change counters; meaningful only while processes run                                 | nothing; a restore starts with none held                      |

A row's kind may be qualified: "SoR (head)" is a Postgres head with a ClickHouse
projection; "SoR, then Derived" is a table that becomes derivable once its wave ships;
"Derived, SoR past its source's retention" and "Derived (SoR for …)" name the rows only
that table holds; "SoR, Coord" and "Cache; SoR (head)" give the kinds of a row's tables
or roles in order.

A Postgres row with a ClickHouse projection is owned by Postgres; the projection is
Derived, rebuilt by republishing the heads (except `datasets`, `documents` and
`knowledge_ingestions`, whose rows ClickHouse alone holds for some keys, so each row
gives its rebuild and its system-of-record rows), and a split table's row gives the kind
of the Postgres half. Postgres stores no vector, so a lost vector table is rebuilt only
by re-embedding every row at provider cost. `memory_versions` is a system of record too:
it holds history written before a deployment's journal existed. The revision metadata in
`memory_revisions` (key, version, hash, status, `seq`) is kept until an erasure deletes
it: a ClickHouse restore's reconcile anti-joins the restored history against it.

`loom.memory` keeps the current text of each key in ClickHouse. It is the source of
`memory_versions_mv`, one of the tables `insights.query` grants, and read by statements
that join it inside ClickHouse; the lexical leg reads
`memory_embeddings.content_excerpt` (`server/memory/app/retrieval/lexical.py`). On a
synthetic namespace of 250k keys, `system.parts` (bytes on disk over rows) measured
about 91 B per row for `memory` (the harness writes one to four version rows per key)
against about 12.9 KiB per row for `memory_embeddings` (one per key; the harness's key
vector is a constant that compresses to almost nothing, so the real figure is larger):
the cost lever is the vectors ([vectors](#vectors-are-the-cost-lever)). To reproduce it,
load, into a ClickHouse of your own, with
`PYTHONPATH=$PWD .venv/bin/python bench/scale_load.py load-ch --shape single --rows 250000`
and run:

```sql
SELECT table, sum(bytes_on_disk) / sum(rows) FROM system.parts
WHERE active AND database = 'loom' AND table IN ('memory', 'memory_embeddings')
GROUP BY table
```

## Cells

A **cell** is one whole Loom deployment ([cells](cells.md)): its replicas and workers,
one Postgres unit, one ClickHouse service and one document store (a bucket prefix, or
`document_blobs` in its ClickHouse where no bucket is configured). Every table on this
page lives in a cell, and a cell shares no store, key, lease or worker with another. Its
signing keys, revoked tokens, service accounts, machine identities, SSO, SCIM and OAuth
state, grants, namespace registry, collections, blacklist (the global `org = '*'`
patterns included), process registry, configuration and secrets are its own, and their
waves move them to its own Postgres beside its memory (each table's Target column). Only
the router's directory is shared, in the router's own Postgres; [cells](cells.md) places
it, with each cell's copy of its own row (`loom.cell_self`). An org lives in one cell
and never leaves it, so this page has no org move, and no fact is split between two
Postgres databases: a check over Postgres tables reads one database, and a grant or
blacklist change commits in the database whose memory commits it fences. (The memory,
knowledge and code planes of the rest of the docs are surfaces of every cell.)

Once they move, security reads (tokens, grants, the blacklist, the registry) go through
caches invalidated by [cache generations](#cache-generations) that fail closed. Sign-in,
sign-up, OIDC-start and workload-token attempt counts (`auth_attempts`) become a
bucketed counter in Postgres, one row per kind, hashed key and window, so admitting a
sign-in reads no ClickHouse. Deployment-wide workers (configuration, the provider
rebuild) run under the cell's own leases. Every org-keyed Postgres table a wave adds
carries the tenancy trigger of [cells](cells.md) in the migration that creates it
(exempting `''`, `'-'` and `'*'`), and enters the schema-generated org list that attach
and `loom doctor` read.

## Statements that cross the stores

A table that leaves ClickHouse breaks every ClickHouse statement that names it. Each
wave's pull request finds them all and rewrites each in one of four ways. It finds:

- every statement by `grep -rnw '<table>'` over the whole repository but the generated
  `schemas/schema.sql`, by the bare name, since some statements name tables without
  `loom.`;
- the materialized views in `schemas/schema.sql` whose source or target is the table;
- code that finds tables at run time through `system.tables` or `system.columns`, such
  as `_STORED_SQL` in `server/core/rmt_carry.py`.

The rewrites:

| Rewrite                         | When                                                                           | Example                                                                                                                                                                                                                             |
| ------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bind a parameter**            | the moved table narrows a ClickHouse read to a small set of keys               | switched-off orgs, open runs, candidate ids                                                                                                                                                                                         |
| **Keep a projection or mirror** | the moved table is joined with large ClickHouse tables or feeds a view         | `memory_records` with `memory_record_fields` (the record side leg), `agent_runs` in the mentor's scans, `namespaces` in worker scans                                                                                                |
| **Split per store**             | one check reads a table in each store while its tables move in different waves | the sign-up check that refuses a name an existing principal holds (`_refuse_empowered` in `server/auth/self_signup.py`): each part reads its store, under the claim that guards it today, until every table it reads is in Postgres |
| **Move together**               | two tables are always read together                                            | `session_briefs` with its revisions                                                                                                                                                                                                 |

The nested claims that guard grant, group, collection and repository changes today
(`grant_change`, `admins_change` and the other claims in `server/auth/grant_claims.py`)
become row locks, taken in today's order, once the rows they guard are in Postgres; a
claim that guards a set (the admins of a namespace, the shape of a collection tree)
locks a named parent row (the namespace's registry row, the org's collection root), so
two changes to the set cannot each see the other's row unchanged. Namespace
auto-registration (`ensure_registered` in
`server/identity/app/namespace_autoregister.py`) decides the owner of the first write
into an unregistered namespace from the namespace census (a ClickHouse read, outside the
transaction) and inserts its `namespaces` row with `ON CONFLICT`. An owned row wins over
an ownerless one and never over an explicit registration, as `ReplacingMergeTree`
ordering decides today. It stays best effort and never fails the write it rides on. A
split check keeps its semantics: the sign-up check still refuses every holder
`_refuse_empowered` checks today (`server/auth/self_signup.py`), a grant, a namespace, a
token, an inbox, a poster rule, a task, and the names a setting grants a role.
`tests/unit/test_package_contracts.py` keeps the store modules separate; each rewrite
lives in the store module of the table that moved.

## Shared Postgres structures

These structures hold the queues, claims, leases, cursors, change counters and the
per-feature state that moves with them; each new one is a table with one library every
caller uses, and the deliveries keep their two existing tables and loops. This page
fixes what each is for, its key, and the requirements its design must meet; the wave
that builds it designs it against them and is reviewed on them.

### Cache generations

`scope_generations (org, scope, generation)` is unchanged. A namespace's row allocates
its revision `seq` under its row lock; that generation bounds the published watermark
that `pg_memory.capture` computes from `memory_deliveries`. `*` is the org's policy
scope, and `('', '*')` the global one.

The change counters that process caches poll get their own table,
`cache_generations (org, kind, generation)`. Its kinds:

- `grants`, `groups` and `collections`, which today's `acl_versions` counts apart
  (`server/core/grant_cache.py`);
- `blacklist`, `revocation` and `config`;
- `namespaces`, the registry, whose narrowing changes answer only once their bump has
  committed, as a grant change does;
- the `table_moves` records (requirement 3's re-read).

Requirements:

- a change bumps its row in its own commit and sends `NOTIFY loom_generation`; a memory
  commit never notifies (a `NOTIFY` takes a database-wide lock at commit);
- a cache listens on a session connection to the primary that bypasses any transaction
  pooler, re-reads on a short TTL when the listener is down, and fails closed past it;
- a cache compares `(restore generation, generation)`, so a counter that climbs back to
  a cached value after a restore still reads as a change;
- the restore generation is a column of the singleton `authority` row, kept apart from
  the paired authority epoch that boot checks (`server/core/pg.py`) and that a restore
  must not change;
- every restore of the cell's Postgres raises it above every value an earlier restore
  set, taken from outside the restored database (the restore's clock in microseconds,
  never the restored value plus one);
- every reader on this page that orders by a restore generation reads this one.

Unauthenticated writes to Postgres are bounded per window, as the KeeperMap key limit
bounds sign-in state today:

- attempt counts in `auth_attempts` for new keys fold into a shared overflow bucket with
  a strict limit, so reaching the bound never refuses a key that already holds a row;
- sign-in state in `oauth_signin_state` (sign-in and device starts), a value read back
  per key, refuses a new key with 429 once its bound is reached, existing keys
  unaffected;
- a client registration in `oauth_state` is admitted per address and refused with 429
  past its bound;
- `/v1/health` reports each bound reached.

**The policy fence.** A memory commit holds its policy scopes shared and starts its
verdict over when one moved (`server/memory/store/pg_memory.py`). Every change that
bumps the policy scope today keeps bumping it (the org's `*` row, `('', '*')` for a
global pattern) in its own commit, in the same database, found by grep for
`pg.bump_policy`, `grant_cache.changed` and `grant_cache.announced` (a grant, group or
collection change through `server/core/grant_cache.py`, a namespace registered,
deactivated, restricted or opted out, an SSO link, a sign-up, a claim release, a
blacklist change), so a verdict judged under the old policy starts over as it does
today. Authorization and blacklist checks read caches, so a request a replica checked
before its cache heard of a change can still commit within the cache's invalidation
bound, today's bound with a poll replaced by a notification.

### Jobs

`jobs (org, id)` in the cell's Postgres replaces the queues built on ClickHouse
(`memory_extraction_queue`, `memory_projection_failures`, `memory_webhook_outbox`,
`code_scip_batches`, `delete_version_checks`), one row per job with a `kind`, a typed
state machine (`ready`, `running`, `done`, `failed`, `cancelled`), a lease and a fencing
token, and the kind's arguments in an opaque `jsonb` payload. Knowledge ingestion is not
a `jobs` kind: it keeps its own `knowledge_jobs`, a named exception: it already holds
its jobs in Postgres with a fencing token and a cancel column, `knowledge_ingestions` is
its ClickHouse projection for reports, and folding it into `jobs` would be a
Postgres-to-Postgres move this page does not need. Requirements:

- **Claim.** `FOR UPDATE SKIP LOCKED` on due rows of a kind, one org per statement, orgs
  taken in turn so one backlog does not starve the rest, and inside an org the kind's
  fairness key in turn (the webhook for `webhook` jobs, as delivery round-robins
  webhooks today, `due_events` in `server/memory/store/webhooks.py`), a webhook's events
  still going out in order, its id their serial key; a claim raises the token and sets
  the lease from the database clock; an expired `running` row is reclaimed in place.
- **Serialization.** A kind that runs one at a time per key (extraction per namespace,
  user and enqueuer while a request is held, as `claim_batch` in
  `server/memory/app/extraction_queue.py` rules today; `knowledge_jobs` keeps its
  one-at-a-time per source) has that key and its held state as typed columns, enforced
  by a partial unique index, with an advisory-lock pre-filter so claims do not wait on
  each other.
- **Dedup.** One ready job per `(org, kind, dedup_key)`; work enqueued while a job runs
  is a ready job of its own, never folded into a run that already read its inputs.
- **Fencing.** Every save and the completion name the token; a job whose effect is a
  Postgres commit locks its row with its token in that commit; effects outside Postgres
  are bounded by the lease, as publications are (`server/core/pg_lease.py`).
- **Transactional outbox.** A job a commit causes (a webhook event, a delete's
  follow-up) is inserted in that commit.
- **Erasure and redaction.** `job_users (org, user_id, job_id)` and
  `job_memories (org, namespace, memory_id, job_id)`, each `ON DELETE CASCADE`, index
  the users and memories a job carries. A user's erasure deletes a job that names only
  that user and, from one that names several, removes the user and scrubs the user's
  content (an extraction job's messages) from its payload; a redaction scrubs the
  redacted text from the jobs that name the memory, matched by namespace and id, since a
  memory id is not unique within an org. A scrub raises the token, and a delete or scrub
  returns the jobs' `lease_until` for the saga's ClickHouse steps to wait out. Jobs a
  memory commit causes are deleted in the memory step's own transaction under the
  scope's lock; the jobs step keeps today's exclusion of the saga's own `memory.erased`
  events (`server/erasure/store/census.py`).
- **Retention.** A kind keeps what its table keeps today: a finished job keeps its row
  for its kind's status op, then the sweep for its kind deletes it on its table's TTL
  today (an extraction job 30 days after enqueue, a `projection_repair` job 30 days
  after it is resolved, one that failed kept until resolved); each attempt is also an
  `events` row.

`memory_code_link_queue` is not merged: the journal already orders every write, so the
code-link worker reads `memory_revisions` from its [cursor](#cursors).

### Deliveries

What a memory or knowledge commit owes ClickHouse stays in `memory_deliveries` and
`knowledge_deliveries`. Those rows are the one publication path: the committing writer
publishes its own delivery under the commit's token (an admission publishes a
namespace's backlog), and the cell's `pg_delivery` and `knowledge_pg_delivery` loops
publish what is left, all under the delivery fencing. Nothing else writes the rows a
commit owes ClickHouse but the `datasets` exception below; rewrites of derived rows in
those tables (a pending-embed row's re-embed, the conflict resolver's version rows, the
provider rebuild's table renamed in whole with writers drained) publish no commit. No
staging table or queue is in ClickHouse. Work a revision owes ClickHouse is a target bit
on its delivery row.

**Journaled heads.** The `shared` and `records` heads join the memory journal: their
revisions are `memory_revisions` rows with a typed `head` column (`memory`, `shared`,
`record`, with typed `schema_name` and `record_id` for a record) that every journal
reader matches on, so record history (`memory_record_versions_mv`) is fed once per
revision and a ClickHouse restore reconciles both like memory; their erasure keeps
today's rules: `shared` is matched by the users it was promoted from, so a shared
revision's sources are a typed index, `revision_sources (org, user_id, namespace, seq)`,
through which a `pg:` census row and the provenance step reach `shared_current` and its
revisions.

**Redaction.** Every table that holds a copy of a version's text is scrubbed by
redaction or its row names why not. In ClickHouse, the rows a model wrote from a
redacted version are matched and retired: the `entity_vectors` rows of the redacted key
for the entities the version's `entity_edge_rows` and `entity_triple_rows` name, matched
by `(entity_text, memory_key)` and rebuilt by the entity projection from the redacted
memory; the `entity_summaries` of those entities, retired and not rebuilt, since no
module writes that table today; the `session_summaries` whose `derived_from` names the
key (any version of it, since the column holds keys), retired and not rebuilt, since a
digest is written from the session's turns; and the `derived_facts` of the version,
matched by the memory `version` that wave 3 adds to them (a fact written before the
column, with no version, is retired with any redaction of its key), retired and not
rebuilt (no column tells a stated operand from an extracted one, and extraction reads
the messages, not the version). These rules are requirements of wave 3, the next wave
that touches redaction. A redaction scrubs a memory version's text wherever a copy of it
lives in Postgres: the version's journal row, `memory_current` (the key's own head when
it holds the text, and the profile heads folded from the memory, as `pg_memory.redact`
does today), `shared_current` when a promotion copied the text, and job payloads
(above); a redaction that reaches `shared_current` also scrubs or republishes the
ClickHouse `shared` rows and the shared-scope `memory_embeddings` rows of that version.
A replay answer in `idempotency` that quotes the text is deleted. Redaction finds it
through `idempotency_revisions (org, key_hash, namespace, seq)`, a typed index of the
revisions each op committed; today they are the `revisions` jsonb
(`server/memory/store/pg_memory.py`). A trigger on `INSERT OR UPDATE OF revisions` fills
the index whatever the build, and the backfill step fills it for existing rows. Until
that backfill is recorded, redaction also matches the `revisions` jsonb.

**Other heads.** The other heads with a projection (`agent_runs`, `operator_edges`) are
republished by a `publish` job their commit inserts, and a task transition owes its
`task_events` row the same way. `agent_runs`' projection keeps today's nanosecond
version, strictly increasing per head, so rows written before the flip never outrank a
later commit and the readers that compare `version` with the clock (`idle_session_runs`
in `server/tasks/store/runs.py`) keep working.

`pg_delivery` itself claims `publish` jobs under the delivery fencing
(`server/core/pg_lease.py`), so each cell has one publication path per journal.
`pg_delivery` publishes the memory journal and every head outside the knowledge plane
that is not journaled. `knowledge_pg_delivery` publishes the knowledge commits and the
`knowledge_ingestions` projection of `knowledge_jobs`; wave 2 moves that projection's
inline insert there.

**The `datasets` exception.** The `datasets` projection of `knowledge_datasets` is a
named exception: its writer inserts it inline after the catalog commit (`insert_catalog`
and `project` in `server/knowledge/store/datasets.py`), as today. The reasons:

- The projection exists for a build that predates the table and a rollback to one
  ([storage authority](storage-authority.md#datasets)).
- A catalog write (a publish, an approval, a carry) commits no document version a
  delivery row could carry.
- A projection that lands after a delete of its source is harmless. A dataset is served
  only while the source's live document row has its version, and the next delete of the
  source removes it (`_delete` in `server/knowledge/app/writes.py`). One that lands
  after an erasure's `documents.tombstone` is found by the residue census, which runs
  the saga again.
- An approval deletes the snapshot it replaced only once the projection has landed
  (`_switch`, `server/knowledge/app/datasets.py`), since until then `loom.datasets`
  still names it for N-1 and a rollback; through a delivery that delete would wait on
  the pass.
- N needs no projection row of its own: a read takes Postgres's rows and only the newer
  rows ClickHouse alone holds (`datasets_repo.at_version`), while N's reports and
  `knowledge.inspect` read `knowledge_ingestions`, which therefore moves to a delivery.

The inline insert of rows Postgres holds retires by rolling-upgrades rule 8 once no
build that predates `knowledge_datasets` can serve; `loom.datasets` then holds only the
rows Postgres cannot store, and the approval's wait on the projection goes with it. The
projection is never rebuilt whole from Postgres, since a row only ClickHouse holds is
its system of record. After a Postgres restore a newer projection row is kept, served
and reported, never deleted. After a ClickHouse restore `loom reconcile` names each
source to ingest again ([backup and recovery](../operations/backup-and-recovery.md)).

**Task events.** For `task_events` the tasks wave meets these requirements: a task's
events land in the order its transitions committed, each lands once (by an `event_id`
column), it is visible before a watcher's cursor can pass it, and `seq` stays a
microsecond stamp (rolling-upgrades rule 4).

**Mirrors.** The `namespaces` mirror, a `code_repos` mirror without credentials and the
`sql_access` mirror, in the cell's ClickHouse, serve the ClickHouse statements that join
them (worker scans, and the security-definer SQL surface views, which leave out
restricted namespaces by them). Each is published by `pg_delivery` as a `publish` job
its head's commit inserts, and is `ReplacingMergeTree(version)` on the head's bigint
commit version, ordered with the restore generation of the cell's Postgres, so the order
rows arrive in does not matter; republishing from the heads rebuilds a mirror after a
restore, and the wave that moves each head builds its mirror before any view reads it
(wave 1 for `namespaces` and `sql_access`, wave 3 for `code_repos`). Two kinds of write
answer only once their rows have landed, else 503 `PUBLICATION_PENDING` with
`committed: true`, as a memory write does, and their replay answers the same until they
land:

- a change that narrows what a scan or a view may take (a namespace deactivated, opted
  out or restricted, or registered restricted, a repository likewise, an SQL-access
  revoke), on its mirror rows, so no row of it is written before the views can leave it
  out;
- a write that is a synchronous mutation today, so that the next read sees it (a
  conversation thread delete, a compaction tombstone, a save and an unsave), on its
  projection rows.

A rebuild swaps in a complete table and never empties the live one. Every projection of
a Postgres head that is not journaled (the mirrors, `agent_runs`, `operator_edges`,
`conversation_states`, `knowledge_ingestions`) is likewise `ReplacingMergeTree` on the
head's commit version; the journal's projections (`memory`, `shared`, `memory_records`)
keep their key's own version and are reconciled after a restore by its anti-join against
`memory_revisions`, and `documents` is reconciled from `knowledge_heads`, a document
with no head kept as restored. `sql_access` grants, its wildcards (`namespace = '*'` for
one org, `org = '*'` for every org) included, reach only the cell's ClickHouse, whose
user a SQL user is.

An erasure saga's steps that change identity tables (`grants.revoke`,
`groups.remove_member`, `personal.retire`, and `collections.forget_owner`) commit in the
cell's Postgres, idempotently, and owe the same cache bumps and mirror rows the change
would owe if an admin made it.

### Conversation state

Messages are an append log read by scans, but today thread delete and compaction
tombstone them, and a save marks them, by mutation (`is_saved`, `saved_at`, and the
saver as `user_id`, `server/knowledge/store/conversations.py`). Wave 3 moves both, a
message's tombstone and its saved state, to Postgres
`conversation_states (org, namespace, agent, thread_id, msg_id)`. Requirements:

- **The saver.** The state row's typed `user_id` is the saver, written only for a
  message whose row's `user_id` is `'-'`, `''` or the saver, by
  `INSERT … ON CONFLICT DO NOTHING` and a read-back, so the first saver of an unowned
  message takes it, as `mark_message_saved` claims today. A message's user is its row's
  `user_id` (the writer) or its state row's (the saver).
- **Readers.** Every statement that reads a moved column (`tombstoned_at`, `is_saved`,
  `saved_at`, or `user_id` as the message's user: a filter, a selected or grouping
  column as in `sql_v1_conversations`, or an export) on `conversations` is rewritten
  onto the state rows, found by grep, its user filters matching either user (among them
  `search_substring`, the erasure exports in `server/erasure/store/exports.py`, the
  thread check of `server/memory/app/evidence_reads.py`, the user-scope census predicate
  and the `conversations.tombstone` user step).
- **The projection.** A ClickHouse projection, `ReplacingMergeTree(version)` and
  published by `pg_delivery`, serves every live read, the saved-only scans and the
  census's live predicate. It has no TTL of its own: its rows leave when their state row
  is deleted and the delete is published.
- **Retention.** A state row is deleted only once no row it governs is left: a message's
  row once its message row is gone from ClickHouse (the sweep takes rows past the
  message's retention expression, `ts` with the global `retention_conversations_days`
  and the per-namespace `retention_days` that `_per_namespace` in
  `server/storage/retention_overrides.py` applies, and deletes only those whose message
  a ClickHouse read no longer finds). The removing `conversation.unsave_message` deletes
  its state row in the same change.
- **Erasure.** The split `conversations.tombstone` runs its ClickHouse step before its
  Postgres step. The Postgres step records the
  `(org, namespace, agent, thread_id, msg_id)` of every message it matched by the saver
  in Postgres `erased_messages` (ids only, swept with the erasure's `erasure_ledger`
  row), and the ClickHouse step's replay after a ClickHouse restore matches those ids as
  well as the row's own `user_id`, with a replay test of a saved `'-'` message in both
  restore directions.
- **Embeddings.** `conversation_embeddings` has no TTL and outlives its messages, so its
  saved state and saver stay on its own rows. Wave 3 replaces today's mutations
  (`mark_message_saved`, and `unsave_message`'s flag clear and removing tombstone) by
  version-row inserts carrying `is_saved`, `saved_at`, `tombstoned_at` and the saver as
  `user_id` (`ReplacingMergeTree(ts)`, the later insert winning a `ts` tie, with today's
  agent-less hand-off rule). The saver's erasure, the census and `conversation_search`
  keep matching the row's own `user_id`.
- **Threads.** `conversation_threads` does not move: its tombstones stay mutations, a
  thread delete's and an erasure's, which set `tombstoned_at` on every version of the
  row. A write that reads the row before a tombstone and inserts after it
  (`conversation.update`, the titler) undoes it; that race is today's code, and no wave
  changes it.
- **No mutations.** Wave 3 rewrites `conversations.tombstone`
  (`server/erasure/store/steps_ledgers.py`) so no statement on `conversations` or
  `conversation_embeddings` is an `ALTER … UPDATE` before the flip's revoke: it deletes
  the messages with their state rows, and tombstones `conversation_embeddings` by
  version-row inserts (`ReplacingMergeTree`). The `conversations` `UPDATE` entry of
  `_EXPECTED_MUTATIONS` (`tests/unit/test_clickhouse_mutation_inventory.py`; the message
  tombstones of `tombstone_thread` and `tombstone_messages`) retires, and its
  `conversation_threads` entry stays; `tombstone_scoped` (whose `conversation_threads`
  statement stays), `mark_message_saved` and `unsave_message` name their table through a
  variable the inventory does not match, so the wave finds them by grep.

### Write marks

`write_marks (org, namespace, surface)` holds the last insert per namespace and surface
(memory, chunk, evidence, record, summary). It serves the namespace sweep and
read-your-writes alike.

- Every write, memory included, sets its surface's mark before it answers, by an
  autocommit `GREATEST` upsert skipped while the mark is within its granularity, so
  concurrent writes coalesce instead of queueing on the row.
- The memory surface's read-your-writes check alone compares the namespace's
  `scope_generations` generation with its published watermark.
- A restore leaves no mark, and a missing mark counts as a write at the restore time, so
  the sweep never purges on its absence.

### Context offloads

`context.offload` stores the only copy of replaced context (`handle_context_offload` in
`server/memory/app/context_offload.py`, up to `context_offload_max_bytes`).

- It becomes a Postgres head, `context_offloads`, of metadata and a pointer. Its bytes
  go to the cell's bucket or, where none is configured, to `offload_bytes` rows the head
  owns, deleted in the head's own transaction (`document_blobs`, shared by every
  document of the same bytes, is not).
- The head carries its writer's expiry (`ttl_seconds` today) as `expires_at`; a sweep
  deletes the head, its object and its rows.
- Its erasure step deletes the objects and rows its heads point to, and the census
  counts them.

### Leases

`leases (org, name)` takes the lease keys of `loom._migration_lock` (every lease caller
of `server/core/leases.py`, and its direct writers,
`server/insights/store/provider_lock.py` and `server/core/schema/migrate_lease.py`); the
table's claim keys follow the claims below, its probe and nonce keys stay ([how a table
moves](#how-a-table-moves)), and the KeeperMap `task_leases` and `agent_run_claims`
become columns and keys of the rows they guard ([merges and
deletions](#merges-and-deletions)). Requirements:

- a take or renewal is one upsert on the database clock; a take draws its token from a
  sequence, so no holder ever reuses one; a renewal keeps it, and a renewal that returns
  another token is a lost lease, whose fresh row the holder releases at once;
- a release deletes only `WHERE holder AND token`; a sweep deletes rows a grace period
  past `until`;
- a lease bounds its holder by time, as today; work that must be fenced against a later
  holder runs as a job and names the job's token;
- a claim that guards one row's change becomes a row lock, a claim that guards a set
  (the admins of a namespace, a collection tree) locks a named parent row, and a claim
  over a key that may not exist yet (a create: `group_change`, `service_account_change`,
  `bot_change`, the sign-up name and email claims, `personal-ns:`) becomes the insert's
  primary-key conflict where its check reads only that table, and otherwise a
  `pg_advisory_xact_lock` on the claim key, taken in today's order inside the change's
  transaction (the sign-up check, `trusts_change`);
- a Postgres restore runs with every process stopped, starts with no lease held (it
  empties `leases`, as for every Coord table) and pairs every token with the database's
  restore generation, so no token issued before the restore, held or lost, compares
  equal to one issued after it.

### Cursors

`cursors (org, consumer, scope)` holds where a consumer stands whose output is not in
ClickHouse: the task webhook's delivery cursor per inbox, with its retry state as typed
columns, and from wave 3 each knowledge source's sync state (its changed-after stamp and
mined revisions, today `knowledge_source:<name>` rows of `code_index_state`), beside the
`knowledge_sources` registry and the `knowledge_heads` it feeds, so a Postgres restore
rewinds both together. A consumer writes its idempotent output, then advances its
cursor. A cursor that records how far a ClickHouse table has been built stays in that
ClickHouse beside the table, in the same backup, so a ClickHouse restore rewinds both,
each ledger set by [the ledger rule](#each-fact-has-one-owner): the code index's build
state (`code_index_state`), the code-link worker's cursor into `memory_revisions` (kept
in `code_index_state`, one per `(org, namespace)` since `seq` is numbered per namespace,
holding a `seq` and never a memory id), the worker resume cursors in `worker_status`,
the tracker's rollup ledger (`qa_rollup_days`) and the usage fold's credits
(`usage_acted_credits`). A cursor into the Postgres journal also records the Postgres
restore generation it was advanced under, and resets (the worker relinks from the heads)
when a Postgres restore has raised it, since a restored journal hands out its `seq`
values again. The provider rebuild's ledger (its table index and cursor, today the
`progress` column of `provider_configuration`) is a named exception: it is in its job's
Postgres row, since its targets are scratch tables of the run, and a ClickHouse restore
fails the job, so the rebuild starts again from its snapshot.

## Schema rules

### Postgres

- **Typed columns for what is read.** Every column a predicate, an index, a guard, a
  constraint or a join reads is a typed column. `jsonb` holds only an opaque, sparse
  remainder the database never filters on (a job's arguments). A `jsonb` field that a
  predicate starts reading moves to a column in that change. The exception is the full
  rows that heads, journals and deliveries keep so every row builder stays unchanged
  ([storage authority](storage-authority.md#rejected-layouts)): `memory_current.row`,
  `memory_revisions.row` and `.audit`, and the `row` of `knowledge_heads`,
  `knowledge_deliveries`, `knowledge_jobs` and `knowledge_datasets`. A field of them
  that a predicate reads (`row->>'memory_type'` in the profile index, the originals a
  knowledge delivery owes) becomes a typed column in the wave that next touches its
  table: wave 3, which adds `memory_revisions.head`, owns `memory_current` and
  `memory_revisions` and types the head fields today's request-path predicates read
  (`tombstoned_at`, `redacted_at`, `sensitivity`, `expires_at`, `status`, `memory_type`,
  and `created_at`, an `ORDER BY` key; `server/memory/store/pg_memory.py`). Each such
  column on an existing table:
  - is filled by a trigger from `row` on every write, whatever the build;
  - is read by N's predicates through `coalesce(<col>, row->><field>)` until a batched
    backfill has set it on every row;
  - on a table that grows with content, is indexed `CONCURRENTLY` by the backfill step
    after it has set every row, never by a boot migration file; the step drops and
    rebuilds an index `pg_index.indisvalid` shows invalid, and no N reader depends on
    the index until it is valid. A content-free or small table may take the boot path
    [migrations](../development/migrations.md) names.
- **`redacted_ts`.** On the journal, `redacted_at` is `text` today, so it moves to a
  typed column over three builds (rolling-upgrades rules 8 and 1: a type change is not
  additive):
  - N adds `redacted_ts timestamptz`, filled by the revision-metadata trigger from
    `coalesce(NEW.redacted_at, NEW.row->>'redacted_at')` (the column a redaction sets
    when `row` is NULL) on `INSERT OR UPDATE OF row, redacted_at`, and reads it through
    `coalesce(redacted_ts, <text>::timestamp AT TIME ZONE 'UTC')`, the text being
    `coalesce(redacted_at, row->>'redacted_at')`, as `pg_memory._meta` falls back today,
    payload included, until the backfill has set it on every revision where that text is
    not NULL.
  - N+1, once the backfill is recorded complete, reads `redacted_ts` alone and neither
    writes nor reads `redacted_at`, except that its trigger still sets `redacted_ts`
    from `NEW.redacted_at`, so a redaction by N during the window is kept.
  - N+2 or later drops `redacted_at` and that clause together.
- **The backfill step** is a leased worker pass that records its completion per column,
  index and check in Postgres `backfill_steps` and never holds the boot's migration
  advisory lock ([Postgres
  migrations](../development/migrations.md#postgres-migrations)); a later file's
  `SET NOT NULL`, a build that reads a typed column alone, and a drop each refuse to
  boot until that record exists, as requirement 9 of [how a table
  moves](#how-a-table-moves) does for flips. A boot migration that waits on a lock held
  by the backfill step's session cancels that session (`pg_cancel_backend`, found by its
  `application_name`), and the step records itself not done, drops any index
  `indisvalid` shows invalid, and retries after the boot; the step holds no transaction
  open between statements (each `CREATE INDEX CONCURRENTLY`, `VALIDATE CONSTRAINT` and
  batch is a statement of its own), so a cancel releases every lock it holds.
- **Stated relations.** Wave 3 keeps the relations a write states (`memory.set`'s
  `relations`, a `memory.bulk_set` entry's, and the facet triples of files, concepts and
  topics) in a typed `revision_relations (org, namespace, seq, ord)` table:
  - one row per stated relation, its subject, relation and object as plain columns, both
    as written and as entity resolution resolved them
    (`server/memory/app/entity_resolution.py`), so a rebuild in revision order is
    deterministic, with a hash index where a lookup by triple needs one;
  - kept as long as the revision's metadata and cascading with it, with a census row
    (`pg:loom.revision_relations`, owned by `pg_memory.delete`), reached by erasure;
  - reached by redaction too, which also scrubs or retires the revision's triples in
    ClickHouse, found through `entity_triple_rows` rather than in the payload, which may
    be NULL;
  - backfilled from `entity_triple_rows` where a row maps to a revision (wave 4's
    row-link backfill backfills it too, for the values it links).

  The triple tables are then derived from it for every relation a revision maps to,
  rebuilt without a model call, and stay the system of record for relations no revision
  maps to.

- **Keys lead with `org`** in every tenant table. Coordination and job tables carry the
  identity they act on (`org`, `namespace`, a job's users in `job_users`, and in its
  payload the rest), not the full tuple. The exceptions are the maintenance indexes of
  the sweeps and claim scans and the cross-org principal index of `namespace_grants`
  (`(lower(subject), org)`, read across orgs by SCIM deprovisioning; the sign-up check
  uses it within its org), which are local to one database, and the tables of the cell
  rather than a tenant, each keyed by what identifies its row there: `signing_keys` by
  `kid`, `sso_links` by `(email, org, namespace)`, `instances` by process,
  `revoked_tokens` by `(kind, key)`, `oauth_state` by `(record_type, id)`,
  `oauth_signin_state` by its claim key, `move_acks` by `(move, process)`, the singleton
  rows, `auth_attempts` by kind, key and window, `scim_users` by its id,
  `machine_identities` by name with an index on `org` for the per-org reads,
  `carry_acks` by process, `table_moves` by move, the configuration tables by their
  ClickHouse key (`deployment_config` by name, `runtime_overrides` by `(kind, key)`,
  `provider_configuration` by `config_id`, `embedder_calibration` by model),
  `analysis_secrets` and `assistant_service` by id, `backfill_steps` by what it sets,
  `pg_migrations` by file, and `cell_probe` by name.
- **Identifiers.** `uuid` for ids made by writers (UUIDv7 where order helps an index),
  `bigint` for sequences and tokens. Text keys stay where they are user-chosen names
  (`memory_key`, `namespace`), with `COLLATE "C"` so ordering and equality match
  ClickHouse byte order. Postgres `text` cannot hold a NUL byte, so a ClickHouse key
  that uses one as a separator becomes typed columns.
- **Checks in the schema.** States, kinds, roles and non-negative counters are `CHECK`
  constraints where the check is cheap; a state column without one today
  (`idempotency.state`, `knowledge_jobs.state`, `memory_revisions.status`) gets it in
  the wave that next touches its table. A check on an existing table is added
  `NOT VALID` (new rows are checked at once) and validated with `VALIDATE CONSTRAINT` by
  the backfill step once it has set every row (never by a boot migration file on a table
  that grows with content), which takes only `SHARE UPDATE EXCLUSIVE`; a later file runs
  `SET NOT NULL` only once that check is validated. A `NOT NULL` on an existing table is
  added the same way as `CHECK (col IS NOT NULL) NOT VALID`; once that is validated,
  `SET NOT NULL` uses it instead of scanning the table, and the check is then dropped
  (`NOT NULL … NOT VALID` exists only from Postgres 18). So no migration scans a large
  table under an exclusive lock. A new value follows rolling-upgrades rule 3: N's
  migration widens the check, N's readers accept it, N+1 writes it.
- **Hot tables.** A table updated in place on the request path or by every pass of a
  worker (`scope_generations`, `leases`, `jobs`, `auth_attempts`, `idempotency`,
  `write_marks`, `graph_inflight`, `instances`, `cursors`, the deliveries,
  `memory_current`) sets, or gets in its wave, `fillfactor` 70 to 90 and keeps the
  columns it updates out of its indexes where it can, so updates stay heap-only; a claim
  index that reads `lease_until` (the deliveries', `jobs`') makes those updates not
  heap-only, which is the price of a partial claim index. A queue or counter sets
  `autovacuum_vacuum_scale_factor = 0` with an absolute threshold, so vacuum runs by
  dead rows, not by table size; a table that grows with content (`memory_current`) gets
  a small scale factor instead, in wave 3. `scope_generations` and `idempotency` take a
  `fillfactor` in the first wave that touches them.
- **TTLs become sweeps.** A table that moves with a TTL keeps it as a sweep on the same
  expression, run under a lease, unless its row names another retention; a KeeperMap
  expiry (`oauth_signin_state`) becomes an `expires_at` column the same sweep reads.
- **Partitioning only when measured.** No Postgres table is partitioned until a
  measurement shows vacuum, a per-org dump or a per-org erasure growing badly; the
  candidates are `memory_revisions` and `jobs`, hash-partitioned by `org`, which keeps
  every org-led key and index; the cross-org maintenance indexes become per-partition.
- **Foreign keys** where one row's life ends another's (a delivery and its revision, a
  supporter and its candidate), with `ON DELETE CASCADE`, and an index on the
  referencing columns, `org` first, wherever the key does not lead with them
  (`job_users`, `job_memories` on `(org, job_id)`; `revision_sources` on
  `(org, namespace, seq)`, which is also the redaction lookup). `idempotency_revisions`
  cascades with its `idempotency` row, whose key its own leads with, and has an
  `(org, namespace, seq)` index for the redaction lookup.

### ClickHouse

- **The sort key leads with the identity tuple** `(org, namespace, …)`, and the
  narrowest prefix every hot read filters on, for every table added or rebuilt; a table
  that stays keeps its key and its engine (the rollups written directly,
  `memory_served_daily`, `query_nodes`, `code_unit_signal`, among them). The deliberate
  exceptions: tables of a cell rather than a tenant (assets by path, `worker_status` by
  worker), the provider caches (tenant rows keyed by model, which keep their key),
  `audit_checkpoints` by window, `loom_telemetry.sli_minute` by SLO class, and the
  `sql_access` mirror by user, which its readers filter by `currentUser()`.
- **Narrowest types.** `LowCardinality(String)` for org, namespace, agent, kinds and
  models; `Enum8` for statuses; `DateTime` unless milliseconds are read;
  `CODEC(ZSTD(3))` on text over a few hundred bytes; `Delta, ZSTD` on monotone integers
  where a measurement shows it pays.
- **Engines by kind.** Append logs are `MergeTree`, with a TTL where retention applies;
  rollups are `AggregatingMergeTree` or `SummingMergeTree` fed by materialized views;
  projections of Postgres state and versioned derived rows are
  `ReplacingMergeTree(version)`, with `is_deleted` only where tombstones are a material
  share of bytes and the erasure census still holds.
- **Graph validity.** The graph tables are also a named exception to the in-place rule
  today: a close or reopen of a triple's or an edge's validity is an
  `ALTER TABLE … UPDATE` (`close_triples`, `reopen_triples` and `end_edges` in
  `server/memory/app/projections.py`); wave 3 moves validity to versioned interval rows
  of their own (`entity_validity`, `ReplacingMergeTree(version)`, [new
  tables](#merges-and-deletions)), while an edge's co-occurrence stays an additive log
  that `entity_degree_mv` sums once per write and interval rows never feed, so a rebuild
  from `revision_relations` and revision order reproduces validity; an offline
  open-facts parity check, which wave 3 builds (`bench/graph_eval.py` calls a model, so
  it is not one), proves results identical, and the change ships default-off where it
  does not.
- **No queues, leases, claims or staging tables.** Anything with a state machine or an
  owner is a Postgres row. A pending-embed row (a vector table's stub with
  `embed_attempts` and `embed_failed_at`, which a worker re-embeds) is not a queue: it
  has no claim or owner, and the re-embed is an idempotent overwrite of a derived row.
  The conflict resolver's mark (`memory_embeddings.conflict_checked_at`,
  `server/memory/store/conflict_resolver.py`) is not a queue either: it rides the row
  its write already emits, no row has a claim or owner, one resolver runs under a lease,
  and a judgement is a new version row of a derived table. `erasure_requests` is a named
  exception: it is ClickHouse's own erasure record, saga checkpoints as version rows
  that the recovery worker resumes without a claim, kept beside the ClickHouse tables it
  erases so that each store keeps its own record (`erasure_ledger` in Postgres) for
  `loom reconcile` ([restores](#restores)). A SCIP upload's parts, which its apply
  worker reads once a batch is complete, are bytes the batch's `code_scip` job owns.
  They go to the cell's bucket keyed by the job, or, where no bucket is configured (a
  single-node deployment), to Postgres `job_parts (org, job_id, seq)`: `bytea` rows of
  at most `code_scip_max_part_bytes` that cascade with the job, the upload refusing a
  batch larger than a per-job byte cap there. A job's parts are deleted when its batch
  is applied, and otherwise by a sweep 7 days after `created_at`, today's TTL, apart
  from the job row's 30-day retention. The sweep finds a part's bucket object by its age
  under the jobs' prefix, so an object whose job is gone is still removed. The provider
  rebuild's snapshot, target, publish and backup tables
  (`server/insights/store/provider_staging.py`) are a named exception to "no staging
  tables in ClickHouse": each is built by one run under an exclusive lease with writers
  drained, no row waits on a per-row publisher, and the publish table is renamed into
  place whole (`RENAME TABLE`, `server/insights/store/provider_publish.py`). A rebuilt
  mirror swapped in whole is the same kind of table.
- **Skip indexes only where a `system.query_log` measurement shows the reads they
  save.**
- **Partitioning on parts and erasure grounds.** A partition key exists only where a TTL
  drops whole partitions or an erasure replaces them. Tables that stay keep their layout
  here; changing a sort or partition key is a rebuild
  ([migrations](../development/migrations.md#changing-a-sort-key-or-a-partition-key)),
  done in its own measured change.

### Vectors are the cost lever

A memory carries two 3,072-dimension `BFloat16` vectors in `memory_embeddings`
(`embedding` and `memory_key_embedding`), 12 KiB of raw values. The codes-first codec
(`Quantized('rabitq', …)`) speeds the scan; it does not shrink the table. Three levers,
each measured with the offline ranking-neutral checks before it ships, and default-off
when it changes ranking:

1. **Whether `memory_key_embedding` earns its bytes.** It serves the key axis of the
   fact leg (`server/memory/app/retrieval/fact_sql.py`) and the goal similarity of
   `procedure.match` (`server/memory/app/procedure.py`), and the offline checks cover
   both: `bench/retrieval_determinism.py --save` before and `--against` after covers the
   fact leg through `memory.search`, on a fixed namespace, identical keys and order (and
   scores within tolerance, which the first wave that uses it adds), and that wave adds
   the same before-and-after comparison for `procedure.match` (fixed namespace,
   identical procedure ids and order). Run it with the axis off; if the results are
   identical, a setting that defaults to writing the column can stop it (half the vector
   bytes). Turning it back on re-embeds the keys at provider cost, so the default stays
   on.
2. **The dimension.** An embedder whose vectors keep their order when truncated can
   store 1,536 dimensions. The width is in each vector column's codec
   (`Quantized('rabitq', 3072, 0)`), so it is a column and codec rebuild, from the
   stored values truncated and renormalised where they are the full-precision prefix (a
   re-embed only where they are not), gated by a setting that defaults to the full
   width, since it changes ranking.
3. **The codec.** Store the codes and a narrower rescoring copy; measure the codec's
   bytes per row and the rescore's recall on the fixtures.

## The ClickHouse tables

Every ClickHouse table, by family: those of `schemas/schema.sql` and, last, the tables
whose names start with `_` that a migration creates, which `scripts/ops/dump_schema.py`
leaves out of it, as it leaves out every `_` name. **Today** is the engine (`RMT`
`ReplacingMergeTree`, `MT` `MergeTree`, `AMT` `AggregatingMergeTree`, `SMT`
`SummingMergeTree`), the sort key, the partition key and whether a TTL applies.
**Target** is where it goes: "stays", a Postgres table, a merge, or a deletion.
**Kind**, from [each fact has one owner](#each-fact-has-one-owner), is the table's kind
in the target layout. **Erasure** is its entry in `server/erasure/store/census.py`: a
census row and its namespace step, a saga step without a census row, or no memory
content; the `_` tables are outside the census. **Wave** is the wave that moves the
table, or the part of it its Target names, or the precondition a table retires on
([waves](#waves)); a table whose Target is "stays" has none
(`tests/unit/test_storage_layout_rows.py`), and its last column names each wave that
changes it in place. The last column names why, and after "named in" up to two modules
where a statement, a table-name literal or a module-level `…TABLE` constant names the
table, docstrings and logger names aside; for a table in both stores, only a module with
no `pg` part in its file name. `_names_table` in
`tests/unit/test_storage_layout_rows.py` holds the exact forms and checks every
citation. A citation names a module, not a symbol, so the test can check it, and
`grep -rnw` finds the other code that names the table ([statements that cross the
stores](#statements-that-cross-the-stores)). The migrator creates `loom._migration_lock`
itself, before any migration file runs; [leases](#leases) places its keys. Tables an
operator command creates for its own run (the provider rebuild's snapshot, target,
publish and backup tables, `server/insights/store/provider_staging.py`) are scratch
copies of tables listed here, owned and removed by that run, and erasure reaches them
(`server/erasure/store/provider_copies.py`).

### How a table moves

Tables move once every deployment records the Postgres memory authority and the
ClickHouse-authority path is deleted: a deployment that still holds memory under
ClickHouse moves first with the authority migration command. The layout depends on it:
`memory` is derived from `memory_current`, `shared` and records join the journal, and
the code-link worker reads `memory_revisions`.

A move is one table, or a group that flips together: the tables one statement reads in
one store, and the tables a cache reads with the counter that invalidates it
(`namespace_grants`, `namespaces`, `principal_groups` and `collections` with
`acl_versions`; `blacklist` with `blacklist_version`; `revoked_tokens` with
`oauth_state`, whose `revocation_owed` rows the revocation cache also reads). No table's
rows are split across the stores, the exceptions being the tables that split by role
(requirement 4) and `_migration_lock` (below). Build N carries both paths for each table
it moves and picks one by the move's recorded authority in `table_moves`; N-1 knows only
ClickHouse. One mover, shared with the authority migration command, runs every move. The
first wave's pull request designs it, and is reviewed on these requirements:

1. **One authority at a time.** Until a table's flip, every build reads, decides, claims
   and writes it on ClickHouse exactly as today, and no reader serves a Postgres copy.
   The coordination tables requirement 3 cuts over are the exception. A table that can
   hold memory content is copied inside its flip, once every writer and saga step on it
   has stopped, or pre-copied under requirement 7's coverage. A content-free table may
   be pre-copied and reconciled at the flip.
2. **The flip is the operator's, after the window.** It starts once no process older
   than N runs, and is a point past which no rollback below N serves, as switching the
   memory authority is (rolling-upgrades rule 33). It runs as a `jobs` row of a kind
   that serializes on one cell-wide key ([jobs](#jobs)), so two flips never overlap; its
   Postgres steps lock the job row with its token, and its ClickHouse steps, bounded by
   the lease as every effect outside Postgres is, are idempotent and re-applied from the
   record (requirement 8), so a late step of a flipper that paused past its lease is
   overwritten.
3. **Every writer stops before the copy.** Every process that can write the table, CLIs
   included, either acknowledges the flip or re-reads the record before each write. A
   process whose registration lapsed stops writing a table with a pending move. The flip
   copies only after every acknowledgement, and once no statement or pending
   asynchronous insert touches the table on any replica. Coordination tables that refill
   on their own are the exception:
   - `instances`, `cell_heartbeats`, `keyring_readers`, `_provider_participants`,
     `carry_acks` and `auth_attempts` are cut over without a copy or a flip, the process
     registry first, before the mover's first flip relies on it;
   - while N-1 runs, N writes both stores and reads ClickHouse, which holds every
     build's rows, so a limit keeps its bound across the window; N reads Postgres alone
     only a full sliding window after the last N-1 write;
   - the rebuild barrier reads ClickHouse while N-1 runs, and `_provider_participants`
     cuts over with no provider transition in flight.
4. **Every stale access fails closed.** The table's name becomes a view that refuses
   every read and write, swapped in atomically so the name is never absent, and no later
   ClickHouse migration touches it. A table that splits into a Postgres head and a
   ClickHouse projection (`shared`, `memory_records`, `agent_runs`, `operator_edges`,
   the `namespaces`, `code_repos` and `sql_access` mirrors) keeps its name, and a mirror
   that leaves a column behind (the sealed credentials of `code_repos`) is rebuilt
   without it and swapped in whole at the flip; a write to it by a process older than N
   after the flip is the rollback the flip forbids. A table that splits by role keeps
   its name for the role that stays (search pages in `context_blobs`, the bytes in
   `document_blobs` where no bucket is configured, the messages in `conversations`, the
   code-index ledger rows in `code_index_state`), and the moved role is refused by a
   guard the flip adds: an insert constraint (no offload row, no catalog column change,
   no `knowledge_source:` key in `code_index_state`) and, for state written in place
   today, the revoke of `ALTER UPDATE` on that table from Loom's ClickHouse user, so a
   stale write of it fails.
5. **One commit decides.** The copy, its verify against the source key by key (inserts,
   updates, and deletes of owned rows the source no longer holds) and the record commit
   in one Postgres transaction. Before it, any failure or a flip past its deadline rolls
   back: the name, the views and the record return to ClickHouse, and the move's rows
   leave Postgres. After it:
   - the old table is kept renamed until it may be dropped ([restores](#restores)),
     listed in one registry of kept tables that the census, erasure, redaction and
     recovery read;
   - the flip classifies the table's saga steps by store ([restores](#restores));
   - each registry row carries the table's own scope predicates, reviewed with its move,
     which, with the mover (requirement 8), is the bounded exception to "no code for the
     old home" until the table is dropped.
6. **The flip deletes only rows its move owns.** A target other writers share (`jobs`,
   `cursors`, `write_marks`) is written only through the move's owned rows.
7. **The window fits the caches and an availability budget.** A content table either
   flips within an availability budget its wave states and measures, or is pre-copied
   with the census, erasure and redaction covering both copies until the flip, so only
   the delta is copied inside it. Every access to the table waits or fails while the
   flip runs, so a request-path table flips within its caches' bound
   (`grant_cache_ttl_seconds`, `acl_watermark_max_stale_seconds`), and each wave's pull
   request measures its flips.
8. **The record survives a restore.** Each move's record is paired with a marker in the
   source ClickHouse, as `storage_authority` pairs with `authority`, and the record is
   authoritative. The marker is written as pending before the flip's commit. On a
   mismatch (a crash between the commit and the ClickHouse steps, a ClickHouse restore
   to before the flip), the mover finishes or re-applies the flip from the record
   (marker, refusing view and kept-table rename) before a process refuses to boot. A
   Postgres restore to before a flip re-runs that flip from the kept copy (copy, verify,
   commit); N+1 and later builds keep the mover with the registry until the kept table
   is dropped. The restored record is never re-applied back to ClickHouse
   ([restores](#restores)).
9. **N+1 depends on every flip.** N+1 refuses to boot while a move N carries has not
   flipped, and carries no code for the old home but the kept-table registry
   (requirement 5) and the mover, which the census, erasure and recovery read until each
   kept table is dropped. A fresh install records every move as flipped and has the
   refusing views, the shape of an upgraded deployment.

`loom._migration_lock` holds keys of callers in more than one wave, so its keys move
with their callers' waves; the keys of callers whose tables stay in ClickHouse move in
wave 2. Each key moves at a flip of its own move, after the window (requirement 2), and
until then every build, N included, takes it in KeeperMap. A moved key is taken in
Postgres alone and the table refuses it by name. The last move retires `run_pass` in
`server/workers/keeper_sweep.py`. The probe and nonce keys the `loom cell` commands
write ([cells](cells.md)) prove the ClickHouse service is the cell's own and live, so
they stay: `_migration_lock` keeps those reserved keys alone, still KeeperMap and still
checked at boot (`require_keeper` in `server/boot.py`) and by `loom doctor`.
`idempotency` does not move: under the Postgres authority every idempotent write op
records in Postgres already (`server/transport/gates.py`), identity and admin ops
included. A table that is deleted rather than moved while a build still reads or feeds
it (`memory_code_link_queue`, whose view fills it until N+1) retires by rolling-upgrades
rule 8: N stops using it, keeping what feeds it while N-1 may read it, and a later
release drops it. A wave-4 merge inside ClickHouse is a backfill of the merged table,
then the same retirement of the old ones.

### Restores

The backup and restore work designs both restores, with the restore drill. This layout
gives it the kind and backup of every table (above), and keeps each move's old table,
renamed and reached by the census, erasure and redaction, until the oldest restorable
Postgres backup postdates the move's flip, so a Postgres restore to before a flip can
recover the table from it. A restore of either store must keep these promises for every
row written before its recovery point, and re-apply every narrowing change and erasure
committed after it:

- No erased row comes back, and no delete its writer committed is undone (a bucket
  object an erasure removed included: the bucket is part of the cell's backup, and a
  document catalog and its bytes are reconciled after either is restored).
- No change that narrows who can authenticate, what they reach, or where an org's data
  may go is undone: an org's model calls switched off, an extraction policy tightened, a
  revocation, a revoke, a group removal, a signing-key retirement or rotation, a service
  account or machine identity removed, a blacklist addition, an SQL-access revoke, a
  namespace restricted, deactivated or opted out. The SQL surface and the scans that
  join a mirror stay closed after a ClickHouse restore until the mirrors are
  republished.
- Every projection of a Postgres head that is not journaled (`conversation_states`,
  `operator_edges`, `agent_runs`, `namespaces`, `code_repos`, `sql_access`, and
  `knowledge_ingestions` from `knowledge_jobs`) is rebuilt whole from its heads after a
  restore of either store, so a projection row of a head the restore lost is not served;
  every read that uses one as a delete or access filter (the SQL surface views, live
  conversation reads, graph joins) fails closed until that rebuild is done. The rebuild
  of `knowledge_ingestions` keeps only the jobs Postgres cannot hold (keys it cannot
  store, or a row a build that predates `knowledge_jobs` wrote), a job whose
  `knowledge_jobs` row the restore lost leaving with it; `datasets` is the named
  exception its row describes.
- No credential issued before the recovery point and spent before the restore (a sign-in
  mark, a code, a device grant, a rotated refresh token) becomes spendable again: a
  Postgres restore invalidates every single-use credential issued under an older restore
  generation, while OAuth client registrations, and the signing keys still active in the
  newest state the restore can re-apply, stay valid.
- Nothing its writer did not ask to delete goes, and writes after the point that a store
  does not replay are reported as lost.
- Since a ClickHouse backup is not consistent across tables, each build ledger is set by
  [the ledger rule](#each-fact-has-one-owner) and each view-fed Derived table is
  reconciled or rebuilt from its source, except a table that is SoR past its source's
  retention, which is only refolded over the source's retained window, never truncated
  or rebuilt whole.

Erasures already keep these promises: each store keeps its own erasure record
(`erasure_requests` in ClickHouse, `erasure_ledger` in Postgres), and `loom reconcile`
runs again in a restored store the erasures and redactions the other records past the
point ([backup and recovery](../operations/backup-and-recovery.md)); no move puts both
records in one store. That holds for a moved table only once its saga steps are
classified by store. The wave that moves a table:

- splits each saga step that touches it into a Postgres step and a ClickHouse step at
  the flip; a step over tables of both stores, such as `curation.tombstone` or
  `records.tombstone`, becomes one of each;
- puts the kept old table's delete in the ClickHouse step, never in a `PG_ONLY_STEPS`
  step, so the replay after a ClickHouse restore reaches it;
- adds the Postgres step to `PG_ONLY_STEPS` (`server/erasure/app/saga_steps.py`, and so
  to the replay's Postgres steps, `server/erasure/app/replay.py`), recording itself in
  `erasure_ledger.pg_steps` in its own transaction;
- makes redaction replay after a Postgres restore scrub every Postgres copy of a
  version's text the layout adds;
- adds its moved steps to the replay tests of both restore directions.

Which record a restore re-applies revocations and the other narrowing changes from, how
that record is written durably before the change answers, and how long it is kept, are
the backup and restore work's design, reviewed on these promises. They bind that work:
until it ships, a cell's restore has a single deployment's limits
([cells](cells.md#what-each-cell-runs)): keys, revocations, sessions, bots and SCIM rows
come back as the backup holds them.

A table that leaves ClickHouse also leaves any step that finds its tables at run time:
`code_index.purge` finds the code tables by name in `system.columns`
(`code_tables_keyed_by_namespace` in `server/code/app/index/retire.py`; it leaves
`code_repos` out today, a registration retired by `active = false`, and keeps doing so),
so the waves that move `code_coverage_watches` and `code_scip_batches` give it a
Postgres part, and the wave that moves `code_scip_parts` has it delete each purged job's
bucket objects before the job row, as the `context_offloads` step does, and wave 4 gives
it the `corpus = 'code'` rows of `term_df` and `doc_lengths`.

Each wave's pull request names its tables, rewrites the statements that read them, runs
the offline ranking-neutral check where search is touched
(`bench/retrieval_determinism.py --save`/`--against`), puts a small local
before-and-after timing in its body, and updates this page's rows and the
rolling-upgrades rules it changes (rules 6 and 9 name ClickHouse leases and ClickHouse
tables for replica-wide state).

## Objections, answered

**"Two stores per request doubles the failure surface."** The security reads move from a
ClickHouse `FINAL` read behind a cache to a Postgres primary-key read behind the same
cache; the request depended on a store for them either way. Once Postgres is required,
every deployment runs it for memory, so the set of stores a deployment depends on does
not grow.

**"The read path gets slower."** Point reads by key get faster: a Postgres primary-key
lookup does not merge parts at read time. The search legs keep reading ClickHouse:
vectors, terms, chunks, the graph and the record projection stay there, and the search
path's Postgres reads are the ones it makes today (the barrier and validation) plus
cached point reads after a cache miss (`namespace_calibration`), and, from wave 2, the
read-your-writes check on `write_marks` and the graph walk's poll of `graph_inflight`,
which move from KeeperMap keys to Postgres point reads. The wave-4 merges touch the
lexical leg's statistics and ship only when `bench/retrieval_determinism.py` shows
identical keys and order, and scores within the tolerance the first wave that uses it
adds.

**"A grant change no longer fences memory writes."** The change bumps the policy scope
in its own commit, in the database where memory commits hold that scope, so verdicts
judged under the old policy start over as they do today; authorization is bounded by the
grant cache's invalidation, as it is today ([the policy fence](#cache-generations)).

**"Moving a table is a migration risk per table."** One mover serves every move, the
authority flips in one Postgres commit per move, and until it does no request path reads
Postgres; only the census, erasure and redaction of a pre-copy do, and the
self-refilling coordination tables of requirement 3. A move that fails its verify rolls
back, and the table stays on ClickHouse.

**"Rolling upgrades break."** Builds N-1 and N both treat ClickHouse as the authority
until no N-1 serves; the flip happens among N's processes only, after every one has
acknowledged it, and the refusing view stops anything that missed it; N+1 boots only
once every move has flipped. Nothing runs a compatibility path past N+1 but the
kept-table registry and the mover (requirements 5 and 8), until each kept table is
dropped.

**"Erasure gets a second place to miss."** A content table is copied inside the flip, or
pre-copied with the census, erasure and redaction reaching both copies; the flip copies
what ClickHouse holds once every process has stopped writing it, and a saga step that
meets the flip retries; from the flip, the census and the saga cover the Postgres table,
and a saga that cannot confirm a deletion fails closed as it does today.

**"`jsonb` everywhere is a schema-less store."** Columns that a predicate, index or
guard reads are typed; `jsonb` holds only what the database never looks inside.

**"One job table is a hot spot."** Claims touch only due rows, skip locked rows, take
orgs in turn, and finished rows leave the claim index at once. A cell where this shows
hash-partitions `jobs` by `org`, which keeps every org-led key and index (the cross-org
maintenance indexes become per-partition).

**"Every cell repeats the deployment-wide rows."** It does, by design: a cell's keys,
revocations, global blacklist and settings are its own, `loom cell each` applies an
org-free admin change in every cell until all succeed, and `loom doctor` names the cells
whose settings differ ([cells](cells.md)). A store shared by the cells would put a
security check, a worker lease, an erasure, a policy generation and the audit chain
across two databases, each needing a protocol of its own.

## Invariants

- A table has one authority at a time, and every build reads and writes it there until
  its flip.
- Every table that can hold memory content is covered by erasure in each store that
  holds a copy, the kept old table of a move included.
- Every cache over a moved table fails closed past its bound.
- A restore keeps the promises of [restores](#restores).
