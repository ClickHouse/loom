# GitHub 트래커 피드

GitHub 피드는 팀의 ClickHouse 데이터베이스에 팀의 트래커 기록을 유지합니다.
Loom의 서빙 프로세스는 기존
[읽기 전용 트래커 소스](https://github.com/ClickHouse/loom/blob/main/docs/features/tracker/record-contract.md)를 통해 그 기록을 읽습니다. 피드는
이슈 본문, 댓글, 풀 리퀘스트를 Loom의 배포 테이블에 넣지 않습니다.

<a id="ownership-and-credentials"></a>

## 소유권과 자격 증명

운영자는 팀의 작업 실행기가 예약한 제한된 CLI 작업으로 피드를 실행합니다.
CLI는 등록된 엔드포인트를 읽거나 기록을 열기 전에, 실제 배포의 설정된 권위 데이터 저장소(ClickHouse 또는 Postgres) 백엔드가 무엇인지, 그리고 자신의 셀이 피드 조직을 보유하고 있는지를 확인합니다.
외부 연결은 이 배포 검사를 다시 수행하며, 기록의 메타데이터를 배포 권한으로 취급하지 않습니다. 작업은 종료 시 두 클라이언트와 배포의
Postgres 풀을 모두 닫습니다.
초기화는 비어 있는 전용 데이터베이스에 피드 테이블과 계약 뷰를 만들며,
이미 존재하는 객체가 있으면 거부합니다. 그런 다음 운영자는 해당 데이터베이스를 별도의 읽기 전용 자격 증명과 함께 트래커
소스로 등록합니다. 구성과 동기화에는 등록된 엔드포인트와 그 리포지토리 허용 목록이 필요합니다. 별도로 제공되는 작성자
자격 증명은 팀의 피드 데이터베이스에만 쓸 수 있으며, 리더 자격 증명은 쓰기용으로 승격되거나 재사용되지 않습니다.

소스 자격 증명은 구성된 리포지토리로 제한된 읽기 전용 세분화된 GitHub 토큰 또는 App 설치 토큰이며, 권한은 Metadata, Issues, Pull requests로 모두 읽기 전용입니다. 토큰 권한은 운영자가 보증하는 구성입니다. GET 성공, 토큰 접두사, 엔드포인트 권한 헤더로는 쓰기 권한이 없음을 증명할 수 없습니다.
식별되지 않은 호스트 토큰은 읽기 전용 라이브 프로브 대상이 아닙니다. 토큰은 팀의
피드 구성 테이블에 기존 secret-root 메커니즘으로 봉인됩니다. 어떤 토큰도 인수, 출력, 계약 뷰에 나타나지 않습니다.
CLI는 이름이 지정된 환경 변수로 데이터베이스 작성자 비밀번호를 받으며,
그 비밀번호를 저장하지 않습니다. GitHub 요청은 고정된 `https://api.github.com` 오리진에 GET을 사용하고, 리디렉션을 거부하며, 검증된 리포지토리 이름과 숫자 항목 ID로 경로를 구성합니다. 응답 URL은 절대 따라가지 않습니다.

팀은 복사된 기록, 백업 보존, 삭제를 소유합니다. 복사된 콘텐츠를 삭제하려면 팀은 예약된 작성자를 중지하고, 영향받는 피드 행, 댓글, 체크포인트를 제거한 뒤 제외 설정과 함께 다시 시작하거나 소스 리포지토리를 제거합니다. Loom 네임스페이스를 삭제하면 Loom의 파생 데이터와 권한이 폐기되지만 팀의 기록은 삭제되지 않습니다. 이는 등록된 다른 트래커 데이터베이스와 같은 경계입니다. 기록 작성자 자격 증명은 Loom 자체 데이터베이스에 접근할 수 없으며, 복사된 콘텐츠는 그곳에 기록되지 않습니다. 로컬인 것은 기존 배포 저장소 리스뿐입니다.

<a id="record-and-progress"></a>

## 기록과 진행 상황

원본 항목과 댓글은 팀의 데이터베이스에 식별 튜플, 프로세스 행위자, 가져온 소스 클래스와 함께 버전 관리됩니다. 계약 뷰는 최신 항목 버전, 계약 UUID, 유효 가시성을 노출합니다. 이슈 및 풀 리퀘스트 댓글은 별도로 보관되며 해당 항목의 검색 가능한 본문에 포함됩니다. 지원되지 않는 트리아지 필드는 계약의 타입이 지정된 기본값을 사용하고, 증거가 생기기 전까지 에지는 비어 있습니다.
계약의 `updated_at`은 항목과 그 댓글 전체에서 가장 최근에 저장된 게시 타임스탬프이므로, 늦은 가져오기와 댓글 수정이 증분 트래커 읽기를 앞당깁니다.
게시 버전은 트래커 커서와 맞추기 위해 정수 밀리초를 사용합니다. 기록의
작성자 리스 아래에서, 각 콘텐츠 배치는 기록 시계와, 모든 리포지토리에 걸쳐 해당 조직에 저장된 모든 콘텐츠 버전보다 1밀리초 뒤인 값 중 더 늦은 쪽을 받습니다.
이 순서는 하나의 커서로 여러 리포지토리를 읽는 네임스페이스에도 적용됩니다.
리포지토리 제어 쓰기도 수신 시계가 뒤로 움직이더라도 해당 조직과 리포지토리에 저장된 버전보다 뒤로 진행합니다. 따라서 가시성 철회, 자격 증명 교체, 커서 체크포인트는 타임스탬프에서 밀리지 않고 이전 제어 행을 대체합니다.
원본 업스트림 타임스탬프는 별도로 유지되며 API 커서를 구동합니다. 모델이나 임베딩 호출은 필요하지 않습니다. 리포지토리 식별자는 API가 다른 대소문자를 반환하더라도 등록된 허용 목록의 표기를 유지합니다.

소유자, 리포지토리 리비전, 게시 워터마크 읽기는
`select_sequential_consistency = 1`을 요청하며, 작성자 리스만으로는 레플리카가 최신이 되지 않습니다. 피드 작성자에는 SharedMergeTree 스토리지 또는 단일 자체 호스팅 서버가 필요하며,
[read-your-writes 보장](https://github.com/ClickHouse/loom/blob/main/docs/architecture/clickhouse.md#read-your-writes)을 따릅니다.
이 설정만으로는 자체 호스팅 복제 테이블에서 확인된 쓰기를 보장하지 못합니다.
작성자 검증은 연결된 기록 데이터베이스의 피드 테이블 다섯 개에 대해 `ReplacingMergeTree`와 `SharedReplacingMergeTree`만 허용합니다. 복제, 분산, 인식되지 않는 테이블 엔진은 작업이 게시하기 전에 거부됩니다.

각 리포지토리에는 독립적인 항목, 이슈 댓글, 리뷰 댓글 커서가 있습니다.
[이슈 엔드포인트](https://docs.github.com/en/rest/issues/issues#list-repository-issues)는
이슈와 풀 리퀘스트를 함께 나열하며, 풀 리퀘스트는 숫자 엔드포인트로 보강됩니다.
[이슈 댓글 엔드포인트](https://docs.github.com/en/rest/issues/comments#list-issue-comments-for-a-repository)와
[리뷰 댓글 엔드포인트](https://docs.github.com/en/rest/pulls/comments#list-review-comments-in-a-repository)는
각각 별도의 갱신 시간 스캔을 가집니다. 각 스캔은 오름차순 `updated_at`, 제한된 페이지, 응답 바이트, 요청 시간을 사용합니다. 커서 진행은 확인된 쓰기만을 따르며 완전한 타임스탬프 경계를 통해 이루어집니다. `since`는 배타적이므로 요청은 저장된 타임스탬프를 1초 낮춥니다. 페이지 예산이 가득 차면 마지막 페이지의 가장 이른 타임스탬프를 저장하고, 다음 턴이 그 경계를 다시 재생합니다. 예산은 2~100 페이지이며, 앞선 페이지는 진행을 허용하고 마지막 페이지는 불완전한 타임스탬프 경계를 유지합니다.
하나의 타임스탬프가 구성된 페이지 예산 전체를 채우면,
작업은 행을 건너뛰거나 진행했다고 주장하는 대신 용량 오류를 보고하고 체크포인트를 유지합니다. 운영자는 해당 리포지토리의 제한된 페이지 예산을 늘릴 수 있습니다.
재생된 행은 같은 식별자를 대체합니다. API는 스냅샷이 아니라 변하는 컬렉션이며,
겹치는 스캔은 트랜잭션 방식의 업스트림 읽기를 주장하지 않으면서 페이지네이션 경합을 줄입니다.

매 턴은 콘텐츠를 복사하기 전에 리포지토리 식별자와 가시성을 검증합니다. 사용할 수 없거나 이동되었거나 일치하지 않는 리포지토리는 먼저 그 리포지토리의 계약 행을 숨긴 다음 해당 턴을 거부합니다. 계약 뷰는 또한 최근의 성공적인 가시성 관찰을 요구하며, 스케줄러가 멈추면 제한된 간격 후 만료됩니다. 각 항목과 댓글 게시는 관찰의 프라이버시 분류를 콘텐츠와 같은 행에 저장합니다. 뷰는 `is_private`와 계약 UUID 모두에 대해 리포지토리, 항목, 저장된 댓글 중 가장 제한적인 분류를 사용합니다. 따라서 리포지토리 메타데이터보다 새 콘텐츠를 먼저 알게 된 레플리카도 비공개 게시를 공개로 표시할 수 없습니다. 표준 트래커의 기존 조건자는 해당 행을 제외합니다. 제한된 네임스페이스는 라이브 직접 권한 검사를 유지합니다. 가시성은 폴링 관찰이며 즉각적인 권한 미러가 아닙니다.
검증된 식별자 불일치나 비공개 관찰은 다른 턴이 리비전을 바꾼 경우에도 현재 기록을 숨길 수 있으며, 이는 현재 자격 증명과 커서를 보존합니다.
이전 자격 증명의 일반 실패는 리비전 검사를 유지합니다. 오래된 공개 관찰은 접근을 넓힐 수 없습니다.

리포지토리가 공개되면 구성 또는 동기화는 공개 메타데이터를 게시하기 전에 기존 스트림 커서를 초기화합니다. 제한된 스캔이 항목과 댓글을 재생하고 각각에 공개 관찰을 기록합니다. 항목은 자신의 행과 저장된 댓글이 재생될 때까지 제한 상태로 유지됩니다. 반복되는 예약 턴은 같은 페이지 및 타임스탬프 경계 제한 아래에서 백로그를 이어서 처리합니다. 삭제된 업스트림 행은 재생할 수 없으므로 팀이 보존된 복사본을 삭제해야 비공개 분류가 해제됩니다.

증분 API 목록은 삭제된 이슈나 댓글을 보고하지 않습니다. 팀이 이러한 삭제를 명시적으로 처리하며, 피드는 삭제 감지를 주장하지 않습니다. 구성, 봉인된 자격 증명, 커서는 팀의 기록에 남으므로 CLI 재시작은 로컬 파일에 의존하지 않습니다. 초기화는 기록을 하나의 Loom 배포의 데이터베이스 UUID에 바인딩하며, 구성과 동기화는 다른 배포를 거부합니다. 해당 배포의 동시 작업은 소스 별칭과 리포지토리 이름 변경과 무관하게 기록 데이터베이스 UUID를 키로 하는 하나의 게시 리스를 사용합니다. 공급자 가져오기는 그 리스 밖에서 이루어지며, 초기화, 구성, 게시는 리스를 공유하므로 동시에 처음 발생하는 식별자 관찰이 직렬화를 우회할 수 없습니다. 불확실한 데이터베이스 쓰기는 제한된
서버 전송 기간 동안 클레임을 유지합니다. 기록을 삭제하려면 팀이 먼저 모든 작성자를 중지해야 합니다.

<a id="validation-and-rollout"></a>

## 검증과 롤아웃

페이크는 페이지네이션 동률, 부분 응답, 속도 제한, 재시도, 가시성 변경, 리디렉션, 자격 증명 마스킹을 다룹니다. 비공개 ClickHouse는 계약, 현재 뷰, 재생, 중단된 커서 게시를 검증합니다. 읽기 전용 토큰이 있으면 제한된 공개 리포지토리 일부를 확인하며, 쓰기 가능한 CLI 토큰으로 대체하지 않습니다.
피드는 Loom 와이어 연산이나 자동 워커를 추가하지 않습니다. 운영자가 피드를 초기화하고 예약하기 전까지 기존 배포와 등록된 트래커는 변경되지 않습니다.

<a id="source-entry-points"></a>

## 소스 진입점

- [CLI](https://github.com/ClickHouse/loom/blob/main/server/cli/tracker_feed.py): `register_tracker_feed`와 `_run`은 소유된
  기록과 별도의 작성자 자격 증명을 선택하며, `_validate_writer`는 권한과
  지원되는 테이블 엔진을 확인합니다.
- [피드 애플리케이션](https://github.com/ClickHouse/loom/blob/main/server/tracker/app/github_feed.py): `initialize`, `configure`,
  `sync`, `_publish`는 소유권을 강제하고, 게시 프라이버시를 기록하며, 쓰기를 펜싱합니다.
- [기록 저장소](https://github.com/ClickHouse/loom/blob/main/server/tracker/store/github_feed.py): `statements`는
  계약 뷰를 정의하며, `repository`, `put_repository`, `put_items`는 게시
  상태를 일관되게 읽습니다.
- [API 클라이언트](https://github.com/ClickHouse/loom/blob/main/server/clients/github_feed.py): `pages`는 업스트림 스캔을 제한하며,
  [도메인 규칙](https://github.com/ClickHouse/loom/blob/main/server/tracker/domain/github_feed.py)은 식별자를 검증하고
  `next_cursor`를 통해 재생 경계를 선택합니다.

<a id="invariants"></a>

## 불변 조건

- 복사된 콘텐츠는 팀이 삭제를 소유하는, 팀의 등록된 기록에 남습니다.
- 리포지토리 식별자, 가시성, 리비전 검사는 콘텐츠 게시보다 앞서며,
  제어 읽기는 지원되는 스토리지 토폴로지에서 확인된 기록 쓰기를 포함합니다.

  UUID는 테이블이 독립적으로 뒤처지더라도 저장된 모든 구성 요소의 분류를 포함합니다.

  전송은 해결될 때까지 클레임을 유지하며, 커서는 확인된 쓰기 이후에만 진행됩니다.

  결합된 항목/댓글 본문이 기존 트래커 커서에 계속 보입니다.
