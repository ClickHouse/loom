# 프로바이더 재구성

Loom은 대시보드 모델 구성을 `loom.provider_configuration`에 암호화된 버전 관리 행으로 저장합니다. 구성에는 커밋된 이전 버전이 하나 있으며, 오래된 버전을 기준으로 한 저장은 거부됩니다. 대시보드에서 설정한 재정의 값은 서버의 시작 시 환경 변수보다 우선합니다. 환경 설정으로 초기화하면 서버가 시작될 때의 스냅샷이 복원되며, 새로 편집한 dotenv 파일은 반영되지 않습니다.

## 활성화와 허용

키 교체와 LLM 전용 변경은 벡터를 다시 빌드하지 않고도 활성화할 수 있습니다.
임베딩 provider, 엔드포인트, 모델 또는 차원을 변경하면 대기 중인 전환이
생성됩니다. 이 전환은 이전 공간의 벡터를 대상으로 활성화되어서는 안 됩니다.

런타임은 실패한 전환을 포함해 완료되지 않은 전환을 관찰하면 로컬 모델 작업 허용 게이트를
닫습니다. 이미 허용된 작업은 끝까지 실행할 수 있습니다. 새 데이터 플레인 요청은 재시도 가능한
점검 응답을 받으며, 워커 패스는 실행 데드라인을 소모하지 않고 대기합니다. 상태 확인, 모델
설정, 대시보드 제어 경로에는 계속 접근할 수 있습니다. 커밋된 일치하는 전환이 있으면 재보정과
허용 재개가 가능합니다. 이후의 키 전용 리비전은 커밋된 선행 체인을 통해 이 검사를 충족할 수 있습니다.

이 게이트는 하나의 프로세스 안의 작업만 셉니다. **분산 쓰기 장벽이 아니며**, 지연된 쓰기나
다른 레플리카가 모두 비워졌다는 것을 증명하지 않습니다.

갱신 루프는 이 게이트 밖에서 코디네이터를 실행합니다. 모든 서버 프로세스와 네이티브 데이터 플레인 CLI
명령은 커밋된 설정을 로드하거나 작업을 허용하기 전에 `loom._provider_participants`에 등록합니다.
전환을 진행하려면 요청, 워커 패스, 등록된 유한 자식 작업, 버퍼링된 쓰기가 모두 비워진 뒤 기존의 모든
참가자가 동일한 설정 ID를 확인 응답해야 합니다. 새로 시작한 프로세스는 서비스를 시작하기 전에
보류 중인 닫힌 게이트 또는 커밋된 대체 설정 중 하나를 로드합니다.

각 참가자는 자체 스레드에서 10 s마다 자신의 행을 기록하며, 참가자가 여는 모든 ClickHouse 클라이언트는
User-Agent에 자신의 id를 명시합니다. 참가자는 스스로 종료했거나(정상 종료), 같은 호스트의 이후
프로세스가 해당 참가자가 사라졌음을 증명했거나, 운영자가 종료 처리한 경우에만 중지된 것으로 간주됩니다.
만료된 하트비트는 증거가 되지 않습니다. 일시 중지된 프로세스는 ClickHouse 밖에서 허용된 작업을 쥐고
있다가 재개된 뒤 이전 설정으로 기록할 수 있으므로, 전환은 해당 참가자가 다시 하트비트를 보내고 작업을
비울 때까지 기다립니다. 각 행에는 호스트 이름, 커널 부팅, 컨테이너 id(Docker의 id 또는 Kubernetes
파드와 컨테이너 이름), pid 네임스페이스, pid, 시작 시간이 들어 있습니다. 각 프로세스는 10 s마다
자신과 같은 호스트와 부팅에 속한 참가자 중 해당 pid가 더 이상 그 프로세스를 실행하지 않는 참가자, 또는
자신의 컨테이너에서 실행되다가 컨테이너가 새 pid 네임스페이스로 재시작된 참가자를, 해당 참가자의 쿼리가
더 이상 실행되지 않을 때 종료 처리합니다. 이는 컨테이너나 워커가 제자리에서 재시작되는, 강제 종료된
프로세스를 포함합니다. 호스트 이름을 공유하는 두 컨테이너(호스트 네트워킹, 한 파드의 두 컨테이너)는
서로를 종료 처리하지 않습니다. 프로세스가 사라졌음을 확인한 운영자는 `loom participant retire --participant <id> --yes`로
해당 참가자를 종료 처리할 수 있으며, 하트비트가 최신이거나 쿼리가 아직 실행 중인 참가자는 거부됩니다.
워커 리더의 `/v1/health`는 전환이 기다리게 될 모든 참가자를 `provider_participants_stale`
(`heartbeat_expired` 또는 `queries_running`)로 나열합니다. `system.processes`는
`clusterAllReplicas(LOOM_CH_CLUSTER)`를 통해 읽으며, 해당 클러스터가 없는 서버는 자기 자신에 대해서만
응답하고, 읽기에 다른 실패가 발생하면 해당 참가자는 실행 중인 것으로 간주됩니다.

제한된 각 리빌드 단계는 공유 설정 Keeper 키를 보유하며, 이 키는 20 s마다 갱신됩니다(TTL 60 s).
경쟁자는 보유자의 참가자가 중지된 것으로 간주될 때만 만료된 키를 인계받으며, TTL이 경과했다는 사실만으로는
증거가 되지 않습니다. `loom
provider-lock clear --holder <holder>`는 참가자 행이 없는 보유자의 키를 해제하며, 보유자가 갱신 중이거나
하트비트를 보내거나 쿼리를 실행 중이면 거부합니다. 부팅 마이그레이션은 이 키 아래에서 실행되지 않습니다.
부팅은 등록한 뒤 완료되지 않은 리빌드가 없는지 확인하는 동안에만 키를 보유하므로, 마이그레이션 중에
시작된 재구성은 부팅이 끝날 때까지 기다립니다. 60 s 넘게 멈춘 참가자는 중지된 것으로 간주될 수 있으며,
다음 하트비트에서 다시 등록하고 다음 갱신에서 게이트를 닫습니다.

첫 번째 코디네이터 체크포인트는 엔드포인트/모델 식별 정보와 유효하게 구성된 프리픽스 너비를 고정합니다.
재시작해도 변경된 프리픽스 설정은 적용되지 않습니다. 리빌드 클라이언트는 명시적 자격 증명을 사용한 원시
provider 요청을 사용하며, 프로세스 캐시와 공유 서빙 캐시를 모두 우회합니다. 형제 요청은 실패한 배치가
소유권을 해제하기 전에 취소를 마칩니다. 활성화는 서빙 보정을 다시 빌드하기 전에 프로세스 캐시 벡터와
이전에 조사한 너비를 지웁니다.

## 리빌드 스테이징

리빌드 인벤토리는 알려진 모든 라이브 벡터 컬럼을 포함합니다. 기록(history) 벡터는 보존되며, 캐시와 파생된 코드 프리픽스에는 별도의 작업이 있습니다. 알 수 없는 벡터 영역은 조용히 누락되지 않고 사전 점검(preflight)에서 실패합니다.

구현된 스테이징 기본 구성 요소는 독점 코디네이터 리스(lease)와 쓰기 작업이 비워진(drained) 라이터를 필요로 합니다:

- 스냅샷 단계의 사전 점검은 어떤 쓰기도 수행하기 전에 영수증, 소스 스키마, UUID를 기준으로 부분 복사본을 조정합니다. 완료되지 않은 소스 복사본은 인벤토리에 포함될 수 있지만 완료된 것으로 인정되지 않고 다시 빌드됩니다. 일치하는 완료된 소스가 없는 대상과 예상하지 못한 비공개 테이블이 있으면 복구가 중단됩니다.
- 소스 복사본은 쓰기 가능한 모든 컬럼을 유지하고 안정적인 페이징 순번을 할당합니다. 완료 영수증은 성공한 복사를 해당 소스의 UUID 및 스키마 핑거프린트에 연결합니다. 확인되지 않은 복사본은 행 수를 근거로 인정되지 않고 다시 빌드됩니다.
- 모델 키 기반 replacing 테이블은 이전 임베딩 레이블 전체에 걸쳐 각 논리 키의 가장 높은 리비전을 선택합니다. 리비전이 같으면 톰스톤(tombstone)을 우선하며, 그다음에는 이전 모델 레이블로 결정적인 타이브레이크를 합니다. 더 나중의 활성 리비전은 명시적 복원을 유지합니다. 선택은 독립적으로 집계한 필드를 섞지 않고 선택된 행 전체를 유지합니다. 소스 정책 버전은 스냅샷 핑거프린트의 일부이므로, 이전 영수증이 변경된 레시피를 조용히 채택할 수 없습니다.
- 스냅샷 정리는 소유권, UUID, 로컬 쿼리 상태를 확인합니다. 쿼리 조회는 생성 시와 동일하게 고정된 ClickHouse 노드를 사용해야 하며, 클러스터 전체의 승인은 아닙니다. 복구 전에 이전 코디네이터는 반드시 차단(fence)되어야 합니다.
- 대상 테이블은 소스 순번을 키로 하는 비공개 `ReplacingMergeTree` 테이블입니다. 반복된 배치는 `FINAL` 아래에서 논리적으로 하나의 행이 됩니다. 소유권 마커는 이 테이블을 소스 스냅샷과 임베딩 공간 핑거프린트에 연결합니다.
- 벡터 생성은 명시적으로 제공된 대상 임베더를 사용합니다. 쓰기 전에 전체 배치를 검증하며, 프로세스 전체의 프로바이더를 변경하지 않습니다.
- 캐시 작업은 소유한 비공개 캐시 대상만 무효화하고 비어 있는지 확인하며, 임베딩 프로바이더를 호출하지 않습니다. 모델 레이블이 바뀌지 않았더라도 이전 엔드포인트별 항목이 무효화됩니다. 제공 중인 캐시는 대체본이 게시될 때까지 그대로 유지됩니다.
- 트래커 페이지는 네임스페이스의 기존 소스 게이트와 일반 인덱싱 레시피를 통해 제목과 본문 텍스트를 가져옵니다. 매칭에는 테넌트, 종류, 항목 번호, 저장소 소스 ID, 저장된 텍스트 다이제스트가 포함됩니다. 톰스톤은 소스를 읽을 필요가 없습니다. 소스는 존재하지만 텍스트가 바뀐 경우, 대상 프로바이더로 보낸 정확한 승인된 텍스트로 스테이징된 텍스트 다이제스트를 갱신합니다. 소유권과 다른 모든 메타데이터는 고정된 채로 유지되며 스냅샷 행은 변경되지 않습니다. 소스가 없거나 접근할 수 없으면 프로바이더 호출이나 스테이징 쓰기 전에 해당 페이지가 중단됩니다. 스냅샷 톰스톤은 소스 읽기나 프로바이더 호출을 유발하지 않습니다.
- 프리픽스 파생은 검증된 재빌드 전체 코드 벡터를 사용하여 ClickHouse 내부에서 메타데이터를 유지하고 일반 프리픽스 정규화 규칙을 적용합니다. 안정적인 순번이 구성된 프로젝션들을 구분합니다. 검증은 행 수만이 아니라 각 레이블의 전체 행 멀티셋을 비교합니다. 고정된 프리픽스 정책이 비어 있으면 더 이상 필요 없는 쌍(twin)을 지웁니다. 매니페스트는 정책을 저장하며, 이와 일치하지 않는 요청은 스테이징을 변경하기 전에 실패합니다. 런타임 활성화는 이후의 키 교체 후에도 완료된 레시피로부터 코드 검색 레이블과 테이블 라우트를 재구성합니다. 프로바이더/엔드포인트 핑거프린트가 일치하지 않으면 수용(admission)은 닫힌 상태로 유지됩니다. 활성화된 프리픽스 기본값은 해당 너비가 재빌드된 경우 그 너비를 유지하며, 없는 너비는 비활성화됩니다. 벡터 기능 캐시는 수용이 다시 열리기 전에 갱신됩니다.
- 스테이징 삽입은 ClickHouse 내부에서 소스 복사본의 변경되지 않은 메타데이터를 직접 선택합니다. Python은 임베딩 관련 업데이트만 전송하므로, 메타데이터를 왕복하는 과정에서 발생하는 시간대 재해석과 타임스탬프 정밀도 손실을 피할 수 있습니다.
- 검증은 행 커버리지, null 안전 메타데이터 동등성, 모델 식별, 벡터 차원, 유한하고 0이 아닌 벡터, 톰스톤의 비워진 벡터를 확인합니다. 검증 결과가 없거나 형식이 잘못된 경우는 성공으로 간주되지 않습니다.
- 검증은 최종 라이브 정렬 키도 확인합니다. 이전 모델의 행이 하나의 모델로 다시 쓰여 replacing 또는 aggregating 엔진에 게시될 때, 서로 다른 스테이징 순번이 조용히 하나로 합쳐져서는 안 됩니다. 정규 입력 선택 이후에도 남아 있는 충돌은 검증 실패로 처리됩니다.

단계 실행기는 효과(effect)가 완료된 후에만 진행 상황을 저장합니다. 프로세스가 데이터베이스 쓰기 후 체크포인트를 저장하기 전에 중단될 수 있으므로 효과는 멱등적이어야 합니다. 실패 시 마지막 커서가 유지되고 고정된 오류 코드가 노출되며, 관리자의 재시도 작업은 같은 전환을 다시 큐에 넣습니다.

진행 체크포인트에는 버전이 지정된 복구 매니페스트도 포함되며, 여기에는 구성 ID, 임베딩 공간 핑거프린트, 고정된 프리픽스 차원, 순서가 있는 전체 테이블 인벤토리가 담깁니다. 프리픽스 정책이 없는 경우를 빈 정책으로 해석하지 않으며, 이전 버전의 매니페스트는 런타임 기본값을 채택하지 않고 실패(fail closed)합니다.
각 항목은 원본 스키마와 UUID, 그리고 스냅샷 및 대상 UUID를 기록합니다. 검증은 이러한 고정된 식별자를 변경하지 않고 준비된 UUID와 검증된 행 수를 추가합니다. 실행기는 게시 전에 이 매니페스트를 저장하고 게시와 정리 단계에 전달합니다. 매니페스트가 없거나, 알 수 없는 버전이거나, 인벤토리가 불완전하거나, UUID가 재사용된 경우 모두 실패(fail closed)하며, 복구는 이름으로 테이블 식별자를 추론하지 않습니다. 매니페스트에는 메타데이터만 들어 있으며 자격 증명, 벡터, 소스 콘텐츠는 포함되지 않습니다.

복구 인벤토리는 정확한 이름과 물리적 UUID가 매니페스트와 일치하는 경우에만 비공개 복사본을 제외합니다. 알 수 없는 벡터 테이블, 다른 작업의 복사본, 이름이 같은 대체 테이블은 여전히 사전 점검에서 실패합니다. 저널에 기록되지 않은 복사본은 이 확인 전에 영수증 조정이 필요하며, 스테이징 프리픽스만으로는 인벤토리를 우회할 수 없습니다. 이 인벤토리 확인은 저널에 기록된 모든 복사본이 여전히 존재함을 증명하지는 않습니다.

벡터 패치는 단일 HTTP 파라미터 필드가 아니라 타입이 지정된 JSONEachRow 멀티파트 파일 데이터로 전달됩니다. SQL 자체가 작더라도 전체 크기의 페이지는 ClickHouse의 폼 필드 제한을 초과할 수 있습니다. 순번과 임베딩 관련 필드만 이 쓰기 경로를 통과하며, 변경되지 않은 메타데이터는 ClickHouse 내부에서 스냅샷으로부터 조인되어 DateTime64 정밀도가 유지됩니다. 업로드는 영구 패치 테이블을 만들지 않으며, 동기 쓰기는 일반적인 재시도 및 중복 제거 설정을 유지합니다.

<a id="publication-primitives"></a>

## 게시 프리미티브

후보 준비 단계는 라이브 스키마를 비공개 테이블로 복제하고, 검증된 스테이징에서
쓰기 가능한 컬럼만 복사합니다. 완료를 기록하기 전에 ClickHouse 내부에서 논리적 행 수와
전체 행 멀티셋 동등성을 모두 검사하며, null과 중복 개수도 포함합니다. 완료된 후보를
재개하면 이 검사를 다시 수행합니다. 행 수가 같다는 것만으로는 복사본이 온전하다는 것을 증명하지
못합니다. 이 헬퍼는 현재 로컬 MergeTree 엔진만 허용합니다. 복제(replicated) 엔진과 공유(shared) 엔진은
별도의 복제 경로 계획이 필요합니다.

코드화된 테이블에서는 준비 단계가 표준 DDL과 기존 Quantized 방식 및 코덱 체인을
유지하고, 테이블 식별자, 소유권 주석, 벡터 너비만 교체합니다. 후보는 서버가 코덱
설정을 받아들이는 방식([제한된 설정](https://github.com/ClickHouse/loom/blob/main/docs/architecture/clickhouse.md#gated-clickhouse-settings))에 따라 생성됩니다. 코덱을 켤 수 없는 경우에는
`CREATE` 전에 거부되며(소유한 오래된 후보는 먼저 삭제됩니다), `allow_suspicious_codecs`를 켤 수 없는 경우에는
체인 없이 생성됩니다. 지워진 스테이징 벡터는 이 물리 컬럼에서 고정 너비의 0
플레이스홀더가 되며, 차원 플래그, 툼스톤 및 기타 메타데이터는 변경되지 않습니다. 전체 행
검증은 행 수가 같은지만 보지 않고 이 명시적 물리 프로젝션을 비교합니다. Rabitq와 TurboQuant의 너비는
8의 배수여야 합니다. 알 수 없는 코덱 인자와 운영자가 만든 벡터 인덱스 또는 제약 조건은
별도의 차원 계획이 필요하며, 준비 단계는 코덱을 제거하거나 호환되지 않는 레이아웃을 게시하는 대신
실패 시 닫힘(fail closed) 방식으로 중단합니다.

게시 헬퍼는 영속적인 원본 테이블 UUID와 준비된 테이블 UUID를 받습니다. 먼저 라이브 테이블을
소유한 백업 이름으로 옮기고, 그다음 준비된 테이블을 라이브 이름으로 옮깁니다. 재시도 시에는 UUID로
이전, 중간, 완료 상태를 식별합니다. `EXCHANGE`는 사용하지 않습니다. 공유 클라이언트의
자동 네트워크 재시도가 응답 유실 후 exchange를 반복하여 이전 테이블을 의도치 않게 복원할 수 있기
때문입니다.

고정된 레시피는 의존하는 명시적 TO 구체화 뷰와 그 교체 UUID도 저널에 기록합니다. 운영자가 작성한
정의에 비밀 정보가 들어 있을 수 있으므로 뷰 DDL은 암호화됩니다. 모든 교체 테이블이 라이브가 된 후
게시 단계는 이 뷰들을 다시 생성하여, 이후 삽입이 백업 UUID가 아니라 교체된 소스에 바인딩되도록 합니다.
DROP/CREATE 응답이 유실되면 저널에 기록된 식별자를 기준으로 재개하며, 알 수 없는 식별자가 있으면 전체
사전 점검이 중단됩니다. 암묵적 내부 데이터가 있는 뷰는 지원하지 않습니다. 이를 삭제하면 데이터가 버려지기
때문입니다. 명시적 TO 뷰의 대상 테이블은 보존되며, 뷰 재바인딩은 백업 정리 전에 완료됩니다.
탐색은 소스 테이블의 `dependencies_database`와 `dependencies_table` 배열을 따르며, 비동기
로딩 의존성은 따르지 않습니다. 뷰 메타데이터가 없거나 데이터베이스 간 의존성이 있으면 실패 시 닫힘
방식으로 중단합니다.

이러한 단방향 이름 변경은 라이브 이름에 일시적인 공백을 남깁니다. 모든 테이블이 게시되고 검증될 때까지
모든 리더와 라이터는 드레인된 상태를 유지해야 합니다. 준비된 테이블은 의도한 라이브 스키마, 인덱스,
제약 조건을 이미 갖추고 있어야 합니다. 서수 키 기반의 스테이징 대상 자체는 게시 가능한 교체본이 아닙니다.
백업 정리와 프로바이더 활성화는 별도의 코디네이터 단계입니다.

정리 단계는 비공개 사본을 삭제하기 전에 모든 라이브 테이블을 저널에 기록된 교체 UUID와 대조해
검증합니다. 알 수 없거나 교체된 사본은 거부하며, 로컬 쿼리와 완료되지 않은 뮤테이션도 확인합니다.
저널에 기록된 정확한 스냅샷, 대상, 백업은 재시도해도 안전한 삭제로 제거되며, 사본이 없으면
중단된 정리를 재개할 수 있습니다. 마지막 식별자 전수 조사에서 이 작업에 속한 사본이 남아 있지
않아야 합니다. 분산 펜스는 여전히 호출자의 책임이며, 호출자는 처리 내내 접수를 닫아 둡니다.

<a id="recovery-and-erasure"></a>

## 복구와 삭제

로컬 런타임 활성화는 임베딩 클라이언트를 변경하고 수신 허용을 다시 열기 전에, 허용된 요청과 등록된 `TaskSet` 작업이 끝나기를 기다립니다. 이 확인은 지연된 쓰기를 취소하지 않습니다. 또한 분산 환경의 확인 응답(acknowledgement)이 아닙니다. 등록되지 않은 작업, 버퍼링된 쓰기, 서버 측 쿼리는 별도의 드레인 확인이 필요하며, 완료되었다는 사실만으로는 쓰기가 성공했음을 보장하지 않습니다.

구체적인 스토리지 백엔드는 스냅샷 매니페스트, 테이블별 재구축, 검증, 교체 준비, 게시, 정리를 지속형 단계 실행기(durable step runner)에 연결합니다. 이 백엔드는 명시적인 임베더, 고정된 정책, 배리어 콜백을 받습니다. 코디네이터 리스를 직접 생성하지 않으며, 분산 환경의 정지 상태(quiescence)를 스스로 증명하지도 않습니다.

부팅 마이그레이션은 프로바이더 설정 펜스 테이블이 생성되면 이를 공유합니다. 전환이 대기 중인 동안 같은 스키마로 재시작하면 마이그레이션 DDL을 건너뜁니다. 대기 중인 마이그레이션이 있는 업그레이드는 해당 전환이 끝날 때까지 기다려야 합니다. 보존 DDL은 모델 작업 게이트를 통해 허용되며, 유지보수 재시작 시에는 건너뜁니다. 변경된 보존 환경 설정은 재구축이 끝난 뒤 다시 재시작하여 적용하세요. MCP 유휴 실행 정리 작업은 유지보수 중에 새 요약 작업을 시작하지 않습니다.

<a id="docker-verification"></a>

## Docker 검증

`scripts/gates/docker_quickstart_smoke.py`는 생성된 릴리스 번들을 새로 만든 일회용 Compose 프로젝트에 설치합니다. 기본 프로덕션 엔트리포인트를 통해 대시보드 로딩, 메모리, 함께 배포되는 컴파일러 툴체인, 영속화된 컴파일러 결과, 재시작, 그리고 문서화된 환경 변수 업데이트/재생성 경로를 확인합니다.

이 게이트의 프로바이더 단계는 Chromium을 사용해 실제 Models & keys 양식을 제출하고, 키를 교체하고, 임베딩 차원을 변경하고, 실패한 재빌드를 재시도하고, 확인 UI를 통해 환경 설정을 복원합니다. 또한 비어 있지 않은 메모리/코드 벡터와 보존된 메타데이터, 두 개의 웹 워커 간 조정, 유지 관리 응답, 장애 복구, 컨테이너 재생성, 비공개 재빌드 복사본의 제거를 확인합니다. 프로바이더 단계는 테스트 전용 Compose 엔트리포인트에서 업스트림 LLM HTTP 엔드포인트만 리디렉션하며, 임베딩 요청에는 네트워크만 사용하는 호환 프로바이더 픽스처를 씁니다. 서버 측 검증, 권한 부여, 암호화, 코디네이터, ClickHouse 저장소는 실제 구성 요소 그대로 동작합니다. 픽스처 자격 증명과 출력은 유료 프로바이더 접근, 모델 품질, 프로덕션 클러스터 동작을 증명하지 않습니다. CI는 이 게이트를 amd64와 arm64에서 실행합니다.

로컬에서 실행하려면 먼저 프런트엔드 의존성과 Chromium을 설치하고(`cd frontend && npm ci && npx playwright install chromium`), 프로덕션 이미지를 빌드한 다음 `--image <repository:tag>`와 함께 게이트를 실행합니다. 이 게이트는 생성된 프로젝트의 컨테이너와 볼륨만 제거합니다. 단위 테스트는 저장소 동작을 모의(mock)한 상태로 이 오케스트레이션을 검증하며, 완전한 Docker 프로바이더 변경 흐름을 검증하지는 않습니다.

코디네이터는 대기 중인 작업을 스냅샷, 재빌드, 검증, 게시, 정리, 활성화 순으로 진행시킵니다. 실패한 작업은 명시적으로 재시도할 때까지 닫힌 상태로 유지되며, 재시도하면 영속 커서부터 재개됩니다. 대시보드 진행 상황에는 단계, 테이블, 카운터가 표시되며, 비공개 복구 매니페스트나 레시피는 노출되지 않습니다.

전환 중에 도착한 삭제 요청은 다른 데이터 플레인 쓰기와 동일하게 재시도 가능한 유지 관리 응답을 받습니다. 그 이전에 시작된 분리형 삭제 사가(saga)는 등록된 유한 작업이며, 스냅샷 이전에 완료되어야 합니다. 잔존 데이터 조사는 모든 재빌드 소스, 대상, 준비된 복사본, 백업도 검사합니다. 이전 replacing 버전과 툼스톤을 포함한 물리적 행을 집계하며, 사용 가능한 스코프 컬럼이 없는 복사본은 모든 스코프에 걸쳐 보수적으로 집계합니다. 알 수 없는 복사본이나 읽을 수 없는 카운트는 0으로 해석되지 않고 검증 실패로 처리됩니다. 복사본은 고정된 레시피 아래에서 수정되지 않고 재빌드 정리 단계에서 제거됩니다. 따라서 중단된 재빌드가 삭제 집계 밖에 스냅샷을 남기거나, 복사본이 대상자의 데이터를 되살릴 수 있는 상태에서 삭제 완료를 보고하는 일이 없습니다.

<a id="current-implementation-boundary"></a>

## 현재 구현 범위의 한계

현재 게시(publication)는 고정된 단일 ClickHouse 노드의 로컬 MergeTree 엔진만 지원합니다. 복제/공유 엔진 준비와 클러스터 전체의 잔여 쿼리 점검에는 아직 별도의 지원 계획이 필요합니다. 따라서 임베딩 공간을 바꾸는 저장 또는 초기화는, 재구축 테이블 중 하나라도 다른 엔진을 사용하고 *동시에* 재임베딩 테이블 중 하나라도 행을 가지고 있으면, 전환이 대기열에 들어가거나 접수가 닫히기 전에 409로 거부됩니다. 상태 응답의 `embedding_change_blocked`에도 같은 사유가 담깁니다.
저장된 벡터가 없으면 어떤 스토리지에서든 재구축할 것이 없습니다. 이 경우 변경은 활성 상태로 커밋되고, 각 프로세스는 구성 새로 고침을 통해 드레인한 뒤 전환합니다. 프로세스가 전환하기 전에 기록한 행에는 이전 모델의 벡터가 그대로 남습니다. Loom에 등록된 서버/CLI 경로 밖에서 데이터베이스에 직접 쓰는 작성자는 운영자가 중지해야 합니다. Loom 프로세스를 집계하는 것만으로는 임의의 외부 SQL 클라이언트를 차단할 수 없습니다. 사망 증명이 없는 원격 참여자의 유실은 명시적인 복구 한계이며, 이를 무시해도 된다는 허용이 아닙니다. Docker 기반의 전체 제공자 변경 및 장애 복구 E2E 검증은 여전히 병합의 선행 조건입니다. 단위 오케스트레이션 테스트와 스토리지 수준 테스트는 그 흐름을 대체하지 못합니다.
